# Intra Relay — Codebase Status Report

_Prepared September 11, 2026. Reviewed at `/Users/mac/Intra` on branch `feat/m10.1-tally-onboarding`._

## What the project is

Intra Relay is a Next.js 15 / React 19 / TypeScript application built for Celo's "Agents at Work" hackathon and since carried well past MVP into a controlled-pilot phase. It bills itself as a merchant-side capability and control layer for WhatsApp-native businesses that have no APIs. The proven slice is narrow and specific: a buyer describes a flyer-printing job, the system turns that into a structured brief, routes it to a verified independent printer, gets a genuine quote back, and hands the buyer a human-approved WhatsApp message to send themselves. The project's guiding document, `CLAUDE.md`, is unusually strict about what it will not do — it never custodies funds, never asks for private keys, seed phrases, bank logins, or ID numbers, never fabricates a settlement or attestation, and never auto-sends a buyer's order. Every requirement in the spec carries a traceable ID (FR-, AC-, BR-, NFR-, G-), and the codebase has no informal TODO/stub markers — incompleteness is tracked deliberately in documentation and in explicit "service unavailable" responses rather than left as dead code.

## Tech stack

Next.js 15.5 (App Router) with React 19 and TypeScript 5.7 in strict mode. Data layer is Drizzle ORM over Postgres, using an embedded PGlite (WASM Postgres) for local development and tests and a real `pg` connection in production — this persistence layer was added deliberately (ADR-006) after the project started as in-memory only. Validation runs through Zod and React Hook Form; styling is Tailwind with a token-based design system. Testing is Vitest plus React Testing Library, with 90-plus test files including unit, integration, and API contract tests. Three notable external integrations were each admitted through their own architecture decision record rather than picked up ad hoc: the Anthropic SDK for a buyer-facing agent model that sits above deterministic policy logic (never holding a tool directly), viem for Celo on-chain calls and EAS attestation schema derivation, and `@x402/core` for a Celo x402 payment adapter. Amplitude handles analytics and `web-push` backs PWA notifications.

## How the modules connect

The app router (`src/app`) exposes both the buyer/operator/supplier-facing pages and a large API surface under `/api` and a public versioned capability API under `/v1/[businessSlug]`. Underneath that, `src/features` holds the actual domain logic, organized as one folder per bounded concern — each typically split into a schema, a repository, a service, and a lifecycle/status module, often with a colocated React panel. The core flow runs: `businesses` (supplier onboarding and route templates) → `routes` (quote-route lifecycle and operator activation) → `quotes` (recommendation, WhatsApp order-message generation) → `tasks` (the buyer's order lifecycle, decisions, exceptions) → `proofline` (physical fulfilment evidence: merchant marks ready, buyer confirms pickup) → `feedback`. Running alongside that spine are `payments` (the x402 query-fee path plus a separate MiniPay on-chain buyer-payment path), `attestation` (EAS-based two-party handover proof on Celo mainnet), `agent` (the LLM-assisted buyer console, with its own model/policy/runtime/console sub-layers), `notifications` and `pwa` (push and installability), and `analytics` (typed event catalogue forwarded to Amplitude). `src/lib` supplies the framework-agnostic plumbing: the Drizzle schema and DB client (which switches between PGlite and real Postgres based on `DATABASE_URL`), shared HTTP request/response helpers, operator API-key auth, and address/slug/formatting utilities. Nine core tables anchor the schema (businesses, quote_routes, tasks, quotes, recommendations, feedback, service_payments, audit_events, proofline_events), with newer tables layered on for idempotency keys, push subscriptions/preferences, and the in-progress onboarding submissions.

## What's actually implemented

The full buyer journey for flyer printing is built and tested end to end: request intake, printer matching, structured briefs, quote generation and revision, buyer accept/decline, WhatsApp handoff message construction, Proofline pickup confirmation, and feedback. Supplier "quick start" onboarding genuinely creates a business and a route in the database, though only through a hardcoded flyer-printing template. Operator tooling exists for verifying and activating routes, viewing metrics and evidence, and managing task exceptions. The x402 Celo payment adapter, the MiniPay on-chain buyer-payment flow, and the EAS attestation writer are all fully coded and covered by contract tests against fixtures. The buyer-agent console (an LLM-assisted layer for classifying intent and holding conversation state) is implemented with its own mock and Anthropic-backed providers. Notifications, push subscriptions, PWA installability, and Amplitude analytics forwarding are all wired up. Test coverage is unusually deep for a project this size — payments, tasks, and agent modules each have on the order of ten or more dedicated test files, and the git history reads like a running list of acceptance criteria being checked off commit by commit.

## What's stubbed, conditional, or incomplete

A few things are real gaps rather than missing polish. The "full" supplier onboarding form (`/supplier/onboard/full`) builds a preview client-side and never submits anywhere — quick-start is the only path that persists a business today, and it never collects a real payout address (it's stored as a zero-address placeholder). There is no API yet for a business to define an arbitrary priced service beyond the flyer-printing template. Payments, attestation, and the agent model are all conditional on external credentials: without an `X402_API_KEY`, paid routes deliberately return a 503 rather than a fake receipt; without a production signer key, attestation degrades to a clearly labeled mock mode; without an Anthropic key, the agent falls back to fully deterministic behavior. None of these are bugs — they're the intended fail-closed design — but they mean the payment and attestation features aren't demonstrable against live infrastructure without setup. Separately, there's a substantial chunk of uncommitted, in-progress work on the current branch: a new "onboarding via Tally webhook" feature (schema, repository, service, signature verification, and a generated but uncommitted DB migration) that the project's own design doc describes as blocked until the Tally form itself gets authorized and an Airtable-based review pipeline is built — right now only the data-contract and webhook-verification piece exists.

## Notable project characteristics

The `docs/` folder functions as the project's real specification system — a PRD treated as source of truth, a 23-entry architecture decision log, API and payments specs, a claims document that explicitly separates "proven," "conditional," and "not built" features, and a large recent frontend audit/redesign package apparently intended to feed an external design tool. The git history shows a disciplined milestone-by-milestone workflow (one feature branch per milestone, each merged individually), and the working tree currently has real in-progress, uncommitted changes for the Tally onboarding feature.

## Suggested next steps

Finishing the Tally onboarding feature is the most immediate unit of work in flight: commit the current schema/migration/webhook changes, then build the Airtable pipeline and operator review step the design doc calls for before this can go live. After that, closing the gap between quick-start and full onboarding — giving suppliers a real path to submit and persist a payout address and to define a priced service beyond the flyer-printing template — would remove the biggest limitation on onboarding new merchant types. On the payments and attestation side, the code is ready; what's missing is operational setup (obtaining and configuring a real `X402_API_KEY` and a production attestation signer key) to move those from "conditional" to "proven" in a live pilot. It would also be worth reviewing the large `docs/frontend-xray/` audit package to decide whether the recommended visual/UX rework should be scheduled now or deferred, since it appears to be a completed analysis phase without a corresponding implementation plan yet. Finally, given how much uncommitted and untracked work is currently sitting in the working tree, committing or stashing it deliberately (rather than letting it accumulate) would keep the milestone-based git history intact.
