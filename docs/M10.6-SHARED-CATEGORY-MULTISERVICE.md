# M10.6 — Shared category vocabulary + multi-service printing onboarding

**Follows**: `docs/M10.3-MARKETPLACE-SUPPLY-MODEL.md` (audit). This milestone
closes exactly the two structural gaps that audit identified (G8, then G1+G2),
in the order the audit itself recommended, and nothing else.

**Status**: code-complete. No migration. No discovery change. No new
templates. No commit made.

---

## 1. Canonical category vocabulary

One identifier space now, shared by both sides:

```
BUSINESS_CATEGORIES (businesses/schema.ts)
  = ["printing", "design", "catering", "delivery", "other"]
  = BusinessCategory   ← the canonical type
```

`intent/domain.ts` imports this same type and retypes
`DomainCapability.category: BusinessCategory`. It is no longer possible for
the demand side to hold a category the supply side doesn't recognise — that
class of bug is now a compile error, not a runtime surprise.

A second field, `DomainCapability.slug: string`, was introduced alongside it.
This is the fine-grained, buyer-facing identifier — what `UserIntent.category`
holds, what `resolveDomain` looks entries up by, and what the model-assisted
classifier (`assist.ts`, ADR-025) chooses between. It is deliberately allowed
to be finer-grained than the canonical category (see §2). Nothing about
`UserIntent`, `extract.ts`, `classify.ts`, or the buyer-facing chips changed —
they operate on `slug` exactly as they operated on the old `category` field.

## 2. Exact demand/supply mapping

| `slug` (buyer-facing, unchanged) | `category` (canonical) | Why                                                                                                                                                                                                                                                                            |
| -------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `printing`                       | `printing`             | Already aligned.                                                                                                                                                                                                                                                               |
| `design`                         | `design`               | Already aligned.                                                                                                                                                                                                                                                               |
| `delivery`                       | `delivery`             | Already aligned.                                                                                                                                                                                                                                                               |
| `food`                           | **`catering`**         | `event-catering-quote` template and the `catering` `BusinessCategory` already exist. "food" was already an alias of this exact entry (`aliases: [...,"catering",...]`) — this makes that implicit link the explicit, typed source of truth instead of inventing a new mapping. |
| `electronics`                    | **`other`**            | No `BusinessCategory`, no `ServiceTemplate` for electronics exists. Mapping it onto its own canonical category would fabricate marketplace supply that isn't there (explicitly disallowed this milestone). `other` is the real, already-existing catch-all.                    |
| `repair`                         | **`other`**            | Same reasoning as electronics.                                                                                                                                                                                                                                                 |

Two entries (`electronics`, `repair`) now share one canonical `category`
(`other`). This is safe and not ambiguous: `resolveDomain` and
`KNOWN_CATEGORIES` never key on `category` — only ever on `slug`/`aliases` —
so each entry keeps its own specific `unavailableNote` ("no electronics
sellers yet" vs. "no repair businesses yet") regardless of which canonical
bucket it reports up to. This mirrors the supply side, where several
`ServiceTemplate`s can already share one `BusinessCategory`.

`ConversationAction.category` (routing.ts, analytics-only — never rendered to
a buyer, verified by grep before this change) now reports the **canonical**
value. A food request's analytics event now says `category: "catering"`, not
`"food"` — this is the entire point: demand and supply now speak the same
language in reporting, not just in code.

## 3. Liveness reconciliation (item 4)

`DomainCapability.serviceable` is no longer hand-typed per entry. It is
derived: `deriveServiceable(routeSlug)` looks up `routeSlug` in
`SERVICE_TEMPLATES` and returns `true` only if that template's
`availability === "mvp"`. Today this produces the exact same values as
before (`printing` → `true`, everything else → `false`), because it always
read the same underlying fact by hand. The difference is there is now
exactly one place that fact lives — `ServiceTemplate.availability` — so a
category can never again _appear_ live on the demand side while no real
supply template backs it. No new liveness system was built.

## 4. Template model (item 5)

```ts
getTemplatesForCategory(category): ServiceTemplate[]   // NEW — every match
defaultTemplateFor(category): ServiceTemplate           // NEW — first match, "other" fallback
getTemplateForCategory(category): ServiceTemplate        // KEPT, now an alias of defaultTemplateFor
```

`quick-start.ts` and `routes/service.ts`'s `createRoute` still call
`getTemplateForCategory` — unchanged behaviour, unchanged call sites. No
caller was migrated to the new names in this milestone; both are available
for whoever adds the first genuinely multi-template category.

## 5. The parameterised printing route (item 6)

**No new route, no new template, no rename.** The existing `flyer-printing`
slug is unchanged — renaming it would have broken every existing discovery
test, seeded business, and capability contract for a purely cosmetic gain,
and it remains the one route the buyer-agent/model pipeline
(`intent/domain.ts`'s `routeSlug`, `agent/model/schema.ts`'s
`intentInterpretationSchema`) knows how to reach. A new slug would have made
every newly-onboarded printer invisible to the one working buyer flow — the
opposite of "commercially meaningful and discoverable."

Instead:

- `routes/printing-products.ts` (new) defines the 14 canonical product
  identifiers (`business_cards`, `flyers`, `posters`, `banners`, `stickers`,
  `brochures`, `booklets`, `invitations`, `apparel`, `packaging`, `labels`,
  `large_format`, `signage`, `documents`) — exactly the 14 Tally already
  collects, none invented.
- `RouteInputField` (`routes/schema.ts`) gained one new optional field,
  `options?: string[]` — the closed set of values a route accepts for a
  field, when it has one. Additive; existing rows have no `options` and
  remain perfectly valid.
- `flyerPrintingInputSchema` (the actual Zod validator a buyer's quote
  request is checked against) gained one new **optional** field:
  `productType: z.enum(PRINTING_PRODUCT_TYPES).optional()`. Optional, so
  every existing buyer flow, the structured form, the model's brief
  interpretation, and every existing test that never mentions `productType`
  continue to validate exactly as before. This also means the field is never
  decorative: if an agent submits it, it is actually accepted and stored —
  unlike the route's purely descriptive `inputSchema`, which the generic
  validator path ignores entirely for this specific slug (`quote-request.ts`
  special-cases `flyer-printing`).

A buyer sending a plain flyer request today needs to do, and change, nothing.

## 6. Tally → route mapping (item 7)

`onboarding/printing-mapping.ts` (new), two pure functions:

- `mapServicesToProductTypes(services)` — maps each submitted Tally service
  label to its canonical product type. A label that isn't one of the 14 known
  services (the free-text "Other" answer) is returned in `unmapped`, never
  silently dropped and never guessed into a canonical type it doesn't match.
- `resolvePricingModel(services)` — see §7.

`onboarding/service.ts`'s `processTallySubmission` now calls
`enrichPrintingRoute` right after `createRoute` (still the same, unmodified
`createRoute` call — one default route, exactly as before). It:

1. Sets the route's `productType` field `options` to the business's actual
   submitted (and recognised) product types.
2. Sets the route's `pricingModel` (see §7).
3. Adds a warning to the submission's `issues` for any unmapped service
   label — visible to the operator, never discarded.

The route remains `DRAFT`. Operator activation and the six-item checklist are
completely untouched — `enrichPrintingRoute` only ever calls `updateRoute`
with `inputSchema`/`pricingModel`, nothing that touches `status`.

`category: "printing"` in `createBusinessFromOnboarding` was **kept**, with a
comment explaining why: the Tally form is still printing-only and asks
nothing that could tell us a different category. Per the milestone's own
condition ("remove only if the new onboarding contract provides the category
correctly"), removing a hardcode with no real input to replace it with would
just be a different hardcode. The code path is no longer structurally
blocking a second category, though — `enrichPrintingRoute`,
`mapServicesToProductTypes`, and `resolvePricingModel` are all category-
agnostic by construction; a future non-printing onboarding form would reuse
the same shape, not fork it.

## 7. Pricing representation (item 8)

A `quote_routes` row has exactly one `pricingModel` — it cannot represent
"business cards are FIXED, banners are QUOTE_REQUIRED" without a new table
(explicitly out of scope). `resolvePricingModel`:

- **All submitted services agree** → that shared model is used directly.
  Verified: a business submitting only `STARTING_FROM` services gets a
  `STARTING_FROM` route (previously it always got the template's arbitrary
  default, `STARTING_FROM`, regardless of what was actually submitted — this
  is now genuinely derived from the submission, not coincidentally correct).
- **They disagree** → the route falls back to `QUOTE_REQUIRED`, the only
  value that never overclaims a specific price the business didn't
  unanimously state, and a warning is added to the submission's issues
  naming the disagreement for an operator to resolve. This previously
  produced **zero** issues and silently used the template default — the
  existing test asserting `issues).toHaveLength(0)` for this exact scenario
  was updated to assert the new warning, with a comment explaining the
  behaviour is deliberately different now.
- `priceAmount`/`priceUnit` are **never** set from free-text `priceText` —
  unchanged from before this milestone. That remains the operator's job via
  the existing `PATCH /api/routes/[id]/pricing` flow, exactly as
  `validate.ts`'s own pre-existing comment already documented.

## 8. Capability contract impact (item 10)

`inputSchemaDescriptor` (`routes/capability.ts`) now passes through a field's
`options` when present and non-empty. Before this change the capability
document would have **silently dropped** `productType`'s options even after
this milestone's other changes — an agent would see a field named
`productType` with no idea what values it accepts. This was caught and fixed
before it could become exactly the kind of "the contract claims one thing,
the code does another" gap the project's own rules warn against.

`CAPABILITY_CONTRACT_VERSION` was **not bumped** (stays `"0.2"`). This is an
additive, optional field on an already loosely-typed nested object — no
existing consumer's expectations break by its presence, consistent with the
project's own "bump on a breaking shape change" convention.

## 9. Backward compatibility

Verified via the full test suite (see the final report) with zero changes
required in:

- `quick-start.ts` / the manual single-business onboarding path.
- `flyerPrintingInputSchema`'s five original required fields, or anything
  that validates against them (`quote-request.ts`, `tasks/service.ts`,
  `StructuredRequestForm.tsx`, `agent/model/schema.ts`).
- `discoverProviders`, `/api/routes/active`, or any discovery semantics.
- The operator activation gate and its checklist.
- Existing seeded businesses/routes (`lib/db/seed.ts` — untouched).

Two existing tests were deliberately updated to reflect intentionally new
(not accidentally broken) behaviour, both explained in their own comments:
`routing.test.ts`'s food/electronics `EXPLAIN_UNAVAILABLE.category`
assertions (now canonical: `catering`/`other`), and
`service.integration.test.ts`'s mixed-pricing-models test (now expects the
warning it previously silently discarded).

## 10. Remaining limitations

- `electronics` and `repair` sharing canonical category `"other"` means an
  operator-facing "group supply by category" view (audit gap G6, still not
  built) would show them together. This is honest given today's real supply
  (there is none for either), not a shortcut that will need undoing later —
  if either ever gets a real template, it gets its own `BusinessCategory` at
  that point, same as `catering` already has one.
- `productType` is optional everywhere by design. Nothing in the buyer
  conversation layer (`intent/`) or the buyer-agent's model-assisted brief
  interpretation (`agent/model/schema.ts`) asks for it yet — that is a
  genuine "AI classification change," explicitly out of scope this
  milestone. A buyer can express a product type today only if they say it in
  free text and an operator/business reads the resulting request manually,
  or once a future milestone wires it into the structured brief.
- 13 of the 14 printing products share one generic input contract
  (`FLYER_PRINTING_INPUT_FIELDS`) rather than each having a tailored brief
  (a banner brief and a business-card brief genuinely differ). The audit's
  own §10.2 recommendation was to start here and promote individual products
  to their own templates only where real discovery demand proves it —
  unchanged.
- A submitted service whose label doesn't match one of the 14 (a free-text
  "Other" answer) is flagged for operator review but not resolved
  automatically. No fuzzy-matching or LLM-assisted mapping was added — kept
  deterministic and conservative per the milestone's constraints.
