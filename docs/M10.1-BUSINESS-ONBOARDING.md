# M10.1 — Remote Business Onboarding: field audit + canonical data contract

**Scope of this document**: Phase 1 of the M10.1 brief (audit) and the
canonical onboarding data contract it must produce before any Tally form is
built. It also carries the Tally form information architecture for the
printing vertical (the one initial form requested), since that design is
downstream of, and must stay consistent with, the audit below.

**Not in this document / not built yet**: the Tally form itself (blocked on
MCP authorization — see the end of this doc), the automation pipeline
(webhook → Airtable → operator review → Intra), Airtable's structure, and any
application code, migration, or new table. Per the brief's own Phase 5: none
of that happens until this design is reviewed.

---

## 0. The single most important finding

**Before designing a new remote pipeline, it's worth being precise about what
"onboarding" currently means in Intra — because it is not one path, and the
richer of the two existing paths does not actually create anything.**

| Path                                                                      | What it collects                                                                                      | What it persists                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Quick-start** (`/supplier/onboard`, `POST /api/businesses/quick-start`) | 12 fields — the only path that actually works remotely today                                          | A real `businesses` row + **exactly one** route, using a hardcoded template for the business's category                                                                                                                                                                                                                                                                                     |
| **Full onboarding** (`/supplier/onboard/full`)                            | 16 fields, richer (service description, service area, opening hours, turnaround, quote-response time) | **Nothing.** `OnboardingForm.tsx`'s `onSubmit` calls `buildOnboardingDraft(values)` — a pure, client-side computation (`persistence: "none"`, confirmed in `draft.ts` and its own test) — and renders a read-only "Capability Card" preview with a single "start over" button. There is no submit action, no API call, no email, no webhook. The data the business just typed goes nowhere. |

This means M10.1 is not "add automation on top of an existing remote pipeline"
— it's "build the first one that actually reaches Intra remotely, richer than
quick-start." That reframes the rest of this document: the canonical contract
below is closer to what full onboarding _tried_ to collect than to what
quick-start actually accepts, and the mapping section (§3) is explicit about
which fields the existing `POST /api/businesses` / `POST
/api/businesses/[slug]/routes` endpoints can take today versus which need an
operator's manual step or a documented future change.

**Second finding, same root cause**: `POST /api/businesses/[slug]/routes`
(`createRoute`) accepts only an optional `templateId`; every other field
(name, description, `inputSchema`, pricing model, price unit, query fee, SLA)
comes from one of exactly five hardcoded `SERVICE_TEMPLATES`
(`src/features/routes/templates.ts`), one per business category. Only
`printing` is MVP-live, with **one** template (`flyer-printing-quote`, size /
quantity / colour / deadline / delivery-area). There is currently no way,
through any existing API, to create a route for an arbitrary business-defined
service with its own name, description, or pricing. A printing business
cannot have "business cards" and "banners" as two independently-priced
services today — only "flyer printing."

This directly affects the brief's "services" multi-select (§4.3 below): the
Tally form can and should ask which print services a business actually
offers, because that's genuinely useful, honest business data and cheap to
collect once — but **only one of those services becomes a live, quoted route
today**, via the existing `flyer-printing-quote` template. The rest is
retained (in Airtable, once that layer exists) as real business data for when
the route model is extended to support arbitrary per-service pricing — not
silently dropped, and not something this document pretends already works.

### 1.6 Never collected, on any path, and this document does not propose adding them

A seed phrase, private key, password, BVN, NIN, card, or bank-login credential
(`FR-SUP-003`, enforced by a dedicated schema test); a home/street address; a
government business-registration or tax ID; social-media follower counts.
None of these are needed to prove "this is a real, reachable business that
can fulfil a request" — the lightweight evidence in §1.5 is.

## 2. The canonical onboarding data contract

**This is not a database mirror.** It is the shape a Tally submission should
normalize into before anything touches Intra — richer than quick-start where
quick-start is genuinely too thin, and honest about which parts map to a real
API today versus which are captured for later.

```
OnboardingSubmission {
  submissionId: string          # Tally's own submission id — the idempotency key (§ automation doc)
  submittedAt: ISO8601

  identity: {
    businessName: string
    category: "printing"        # fixed for this form; future forms add other categories
    contactName: string
    contactChannelType: "whatsapp" | "email" | "phone"
    contactChannelValue: string
    city: string
    country: string              # default "Nigeria"
  }

  location: {
    serviceArea: string          # free text — areas served / delivery radius
    pickupAvailable: boolean
    deliveryAvailable: boolean
  }

  services: [                    # 1..N — see §0 on why only one becomes a live route today
    {
      serviceKey: string          # e.g. "business_cards", "flyers", "banners", "other"
      serviceLabel: string        # shown to the business; free text when serviceKey = "other"
      pricingModel: "FIXED" | "STARTING_FROM" | "QUOTE_REQUIRED"
      priceAmount: number | null        # required unless QUOTE_REQUIRED
      priceUnit: string | null          # e.g. "per 100", "per piece" — null for a flat job price
      currency: "NGN"                    # fixed for this pilot
      minimumOrder: string | null        # free text, e.g. "50 pieces" — explicitly optional
      priceChangingFactors: string | null # free text, e.g. "paper stock, quantity tier"
      turnaround: string           # required — this is a quoting/fulfilment input, not optional
    }
  ]

  capacity: {
    quoteResponseTime: "30m" | "2h" | "same_day" | "next_day"
    operatingHours: string
  }

  payment: {
    hasPayoutAddress: boolean
    payoutAddress: string | null      # ONLY when hasPayoutAddress — never a placeholder
  }

  verification: {
    evidenceType: "social_page" | "google_business" | "website" | "photos" | "other"
    evidenceValue: string              # a URL, or a note for "photos"/"other"
  }

  consent: {
    agreedToMarketplaceTerms: boolean  # blocking
  }
}
```

Why each top-level group exists, briefly: `identity`/`location` are the
discovery minimum (§1.1–1.2); `services` is the real gap this milestone
closes, one entry per service the business actually offers, each carrying its
own structured pricing rather than one blob (directly answering the brief's
"do not rely on a single free-text price field"); `capacity` is quoting
context, not a capacity-management system; `payment` is deliberately a
three-state fact (`hasPayoutAddress: false` / `true` with a real address —
never a placeholder in between); `verification` is lightweight evidence, not
KYC; `consent` is the one blocking checkbox.

| Contract field                                                     | Where it goes today                                                                                                                                                         | Notes                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `identity.*`                                                       | `POST /api/businesses` (`createBusinessRequestSchema`) — direct 1:1                                                                                                         | Already exactly this shape.                                                                                                                                                                                                                                                                           |
| `location.serviceArea`                                             | **No column today.** Kept in the operator's review record; not lost, just not yet structured in Postgres.                                                                   | Candidate for a future `businesses.serviceArea` column — not proposed in this milestone (no migrations, per the brief).                                                                                                                                                                               |
| `services[0]` (the operator's chosen best-fit service)             | `POST /api/businesses/[slug]/routes` with `templateId: "flyer-printing-quote"`, then `PATCH /api/routes/[id]/pricing` for the real `pricingModel`/`priceAmount`/`priceUnit` | Only the first, operator-selected service becomes a live route (§0). The other entries in `services[]` stay in the review record as real business data for when routing supports more than one template-defined service.                                                                              |
| `services[*].minimumOrder`, `.priceChangingFactors`, `.turnaround` | **No column today.**                                                                                                                                                        | Shown to the operator during review (so they can factor it into how they talk to the business) and to future development, not silently discarded.                                                                                                                                                     |
| `capacity.quoteResponseTime`                                       | Template default only — nothing accepts an override today                                                                                                                   | An operator cannot currently tighten/loosen the SLA per business through any API; flag, don't build.                                                                                                                                                                                                  |

| `verification.*`                                                   | Operator's own record (no `businesses` column for this)                                                                                                                     | Reviewed manually, same as today's activation checklist.                                                                                                                                                                                                                                              |
| `consent.agreedToMarketplaceTerms`                                 | `POST /api/businesses` `consentToQuoteDisplay`                                                                                                                              | Direct 1:1.                                                                                                                                                                                                                                                                                           |

**No existing onboarding API is modified by this document.** Every write
above is a call already covered by the existing test suite; where the
contract can't map to anything, that's stated plainly rather than invented.

### 4.7 Marketplace readiness & consent

Plain explanation (not a question — shown as text): customers submit real

| Field   | Question                                                                                                                          | Type     | Required |

### 4.8 Conditional logic summary

- `services_other_detail` only if `services_offered` includes "other."
- The per-service pricing group repeats once per item in `services_offered`.
- `{service}_price` / `{service}_price_unit` only if that service's pricing
  model is `FIXED` or `STARTING_FROM` (skipped for `QUOTE_REQUIRED`).
- `payout_address` only if `has_wallet` = yes.

Nothing else branches — everything else is asked once, in order, because
skipping it would either lose required discovery/quote data or ask a
follow-up nobody would actually branch on.

## 5. What this document deliberately does not do

- Does not create the Tally form (needs the Tally MCP connection —
  registered this session at `https://api.tally.so/mcp`, but it requires an
  interactive OAuth authorization this session cannot complete; see the
  chat response for the exact next step).
- Does not build the automation pipeline, Airtable base, or any n8n/webhook
  wiring — that's the next design pass, after this contract is reviewed, per
  the brief's own Phase 5.
- Does not touch application code, migrations, or existing onboarding APIs.
- Does not invent a per-service routing capability that doesn't exist —
  §0/§3 say plainly where the current system's one-route-per-category limit
  bites, rather than building around it silently.
