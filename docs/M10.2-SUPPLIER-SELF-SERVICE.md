# M10.2 — Supplier reachability, self-service & capability visibility

**Scope**: three supplier-side gaps found after M10.1 went live — a merchant can
lose their manage link with no way back, cannot correct their own details, and
cannot see how buyer agents actually see them. Nothing about the M10.1 Tally
pipeline, the buyer flow, quoting, payments, or attestation changes.

---

## 1. The existing supplier access flow (traced before changing anything)

### 1.1 The manage token

| Question                         | Finding                                                                                                                                                                                                                                        |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Generated where                  | `businesses.manage_token` (`src/lib/db/schema.ts:108`) — a column default: `replace(gen_random_uuid()::text, '-', '')`, with a matching `$defaultFn` for the JS path. Nothing else ever sets it; there is no rotation path.                    |
| Stored where                     | One column on `businesses`. Never duplicated anywhere else.                                                                                                                                                                                    |
| Validated how                    | `src/features/businesses/access.ts` — four scoped helpers (`…MatchesBusiness`, `…MatchesBusinessSlug`, `…MatchesRoute`, `…MatchesTask`), each doing a single-row lookup then `timingSafeEqual`. No route trusts a client-supplied business id. |
| Presented how                    | Two ways: as `?t=<token>` on `/supplier/[slug]*` pages, and as the `x-manage-token` header for API calls (`src/lib/http/operator.ts` `getManageToken`, sent by `src/lib/api.ts:41`).                                                           |
| Leak protection already in place | `toPublicBusiness()` (`src/features/routes/reads.ts:25`) strips `manageToken` from every workspace/operator read; `src/features/agent/trace.ts:50` lists it as a redacted key.                                                                 |

### 1.2 Where a merchant can currently obtain it

- **Quick-start only.** `quickStartBusiness` returns `manageUrl:
/supplier/<slug>?t=<token>` (`src/features/businesses/quick-start.ts:167`),
  rendered once by `QuickStartForm.tsx` as a link labelled "Open your
  workspace" plus a "Keep this link" callout. There is **no copy action, no
  share action, and the raw URL is never shown as text.** Navigate away
  without bookmarking and it is gone.
- **M10.1 Tally onboarding: nowhere at all.** `createBusinessFromOnboarding`
  (`src/features/onboarding/service.ts`) creates the business — so a token
  exists — but nothing returns or surfaces it. The merchant is in Tally, not
  in Intra, and the Tally thank-you page is static, so it cannot carry a
  per-business URL.
- **Operator: nowhere either.** `listOperatorQueue` and
  `GET /api/operator/onboarding` both run through `toPublicBusiness`, which
  strips the token. Today **no human can recover a lost manage link** without
  a direct database read.

### 1.3 Why notifications cannot be the recovery channel

`notify()` (`src/features/notifications/service.ts:138`) writes a
notification row and optionally sends real web push (VAPID). Business-audience
notifications already deep-link **with the token embedded**
(`catalogue.ts:56`). But a business reads those notifications through
`ActionCentre`, which is rendered on the supplier page and authorised by
`businessSlug=<slug>&t=<token>` — **reaching the notification requires the
manage link already**. Chicken-and-egg: notifications cannot deliver the thing
that unlocks notifications.

### 1.4 Outbound messaging reality

There is **no outbound messaging capability in this application.** No Twilio,
Vonage, MessageBird, Resend, or equivalent — the only delivery dependency is
`web-push`. The single WhatsApp touchpoint in the codebase is a `wa.me` deep
link built inline in `TaskPage.tsx:870` that a **human buyer** chooses to
open, alongside a local copy-to-clipboard closure (`TaskPage.tsx:877`). The
product copy states this explicitly: "Intra does not send this message and
never pays a supplier for you."

**Consequence for this milestone**: a "we WhatsApp the merchant their link"
feature would require inventing an integration that does not exist. This
milestone does not build one. It builds share/copy actions that work from
whichever human's device is already holding the link — exactly the mechanism
the buyer handoff already uses.

### 1.5 What the merchant can see about themselves today

`/supplier/[slug]/review` renders a read-only `DataList` (contact name, order
channel, currency, payout address, consent, verification) and a **hand-written
prose block** titled "What agents can see when this route is Active". That
prose is a second, hardcoded description of agent-facing data — it can drift
from what `/v1/[slug]/capabilities` actually returns, and it is not derived
from it.

## 2. What this milestone changes

See §3 onward. In one line each:

- **A — recoverable link**: the manage link becomes visible, copyable and
  shareable to the merchant who holds it, and recoverable by an operator for a
  merchant who has lost it — through one narrowly-scoped, operator-gated,
  audited endpoint. No new auth system, no fake messaging integration.
- **B — self-service**: four safe profile fields become merchant-editable
  through the existing manage-token authorisation and the existing domain
  validation schema. Everything operational stays operator-only.
- **C — capability preview**: the supplier sees a human-readable rendering of
  the _same_ `buildBusinessCapabilities()` document agents read — the existing
  hardcoded prose block is replaced, not supplemented.

---

## 3. A — the manage link

`src/features/businesses/manage-link.ts` is now the one definition of the link
shape (`quick-start.ts` was rewritten to call it; the notification deeplink in
`catalogue.ts` is a different path and was left alone). It also builds the
plain-language message a human sends and the `wa.me` deep link that opens
WhatsApp on that human's own device.

Three places a link can now be obtained:

| Who                                   | Where              | How                                                                                                                                                                             |
| ------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A merchant already in their workspace | `/supplier/<slug>` | `ManageLinkCard` renders the link they arrived with — copy, or "send it to myself on WhatsApp". Reconstructed from the token in the URL; it is never re-read from the database. |
| A merchant finishing quick-start      | The success screen | Same card, worded "Save your private link now — this is the only time we show it".                                                                                              |
| A merchant who lost it                | Their operator     | `GET /api/operator/businesses/<slug>/manage-link`                                                                                                                               |

The recovery endpoint is the only place in the application that deliberately
returns a live credential, so it is narrow by construction: operator-key gated,
**one named business per call** (a token can never ride along in a list
response), and every retrieval appends `business.manage_link_recovered` to the
audit trail — recording who asked and for which business, never the token
itself.

**What was deliberately not built**: outbound WhatsApp. There is no messaging
provider in this application (§1.4) and this milestone did not invent one. Every
"send" action is a `wa.me` link a human chooses to open, exactly like the
existing buyer order handoff.

## 4. B — merchant self-service

`updateBusinessProfile` (`src/features/businesses/profile.ts`), exposed as
`PATCH /api/businesses/<slug>/profile`, manage-token only.

**Editable**: business display name, contact name, contact channel value
(the WhatsApp number that receives orders), city.

**Not editable, and structurally unreachable**: verification state, business or
route status, payout address, consent record, quote currency, category, slug,
manage token, pricing, services, onboarding status, buyer decisions, metrics,
internal ids. The patch object is built field by field from the four parsed
values, so an unexpected key cannot reach the database even if a hand-rolled
request sends one — there is a test that sends exactly that.

`slug` is absent on purpose: it is the business's public identity
(`/supplier/<slug>`, `/v1/<slug>/capabilities`, every route's stored
`endpoint`). A merchant renaming their business changes what customers read,
never what their existing links resolve to.

Validation is `businessOnboardingObject.pick({...})` — the same rules and the
same error messages the merchant saw when they first typed these values. The UI
restates none of them; the server is authoritative and its messages are
rendered verbatim.

Each save appends `business.profile_updated` recording **which fields changed,
never their values** — a contact number is the merchant's personal data and the
audit trail is read more widely than they are.

## 5. C — how buyers find you

`AgentProfilePreview` takes a `BusinessCapabilities` — the exact object
`buildBusinessCapabilities()` returns and `/v1/<slug>/capabilities` serves. The
review page calls that function and passes the result straight in. The
component re-words; it never recomputes availability, pricing, or contact
exposure, so there is no second representation to drift.

It shows what is published (identity, location, each service with the
document's own `pricing.summary` string, promised reply time, and whether the
order contact is being given out) and, separately, what is **kept private** —
the manage link, the merchant's own performance record, operator notes, and the
order contact while nothing is live. "View agent profile" links to the raw
endpoint for anyone curious, but the human page is primary.

Verified live at a 375px viewport against a business whose route was still
`DRAFT`: the capability document had no `orderContact`, and the preview
correspondingly said "Not given out while this service is not live" and
rendered the merchant's phone number nowhere.

## 6. D — the M10.1 seam

`GET /api/operator/onboarding` now joins each processed submission to its
business `{ slug, name }` and includes the `manageLinkEndpoint` to call for it.
Without the slug an operator looking at a Tally submission had no way to name
the business they needed to send a link to — that was the missing step between
"business created" and "merchant can get in".

The lifecycle now runs end to end with nothing added to it:

```
WhatsApp link → Tally → webhook → business + service/pricing → NEEDS_REVIEW/PROCESSED
   → operator retrieves the manage link and sends it on
   → merchant opens their workspace, corrects their details,
     sees how buyers find them
   → operator activates → pilot-ready
```

A replayed webhook keeps the same business **and the same manage token**, so a
link already handed to a merchant cannot stop working because Tally retried.
