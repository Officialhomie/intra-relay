# 02 — Complexity Abstraction Audit

> Classifies every meaningful piece of product complexity against the principle:
>
> **EXPOSE USER INTENT · ABSTRACT IMPLEMENTATION COMPLEXITY · PRESERVE NECESSARY
> CONTROL AND TRANSPARENCY.**
>
> This is a documentation pass, not a redesign. "Recommended abstraction level"
> records what _should_ be visible vs hidden given the product's own safety rules
> (`CLAUDE.md` §4, `docs/UX_ARCHITECTURE.md` §2) — it does not propose UI.
>
> The **abstraction boundary** (`docs/UX_ARCHITECTURE.md` §2) is absolute: a step
> required for security, financial consequence, permission/consent, irreversible
> action, privacy, legal/compliance, or a genuine human trade-off **must stay
> visible and manual**. Simplify only its _presentation_.

---

## Legend

- **USER-RELEVANT** — the user genuinely needs to know this.
- **USER-DECISION** — requires explicit human judgement or consent.
- **SYSTEM-IMPLEMENTATION** — backend / frontend / AI / chain plumbing done
  automatically.
- **MUST REMAIN HIDDEN** — technical detail that should not normally appear.
- **MUST BE EXPLAINED** — technical detail that affects trust, money,
  permissions, timing, or a user decision.
- **CURRENTLY EXPOSED** — shown to users today (with the file).
- **CURRENTLY ABSTRACTED** — already hidden today (with the file).
- **POTENTIAL UX PROBLEM** — a place users are forced to understand
  implementation unnecessarily.

# 4. What is CURRENTLY ABSTRACTED (already hidden — do not "un-hide")

- Every internal enum → a plain label (`taskStatusLabel`, `routeStatusLabel`,
  `QUOTE_STATUS_COPY`, `PROOFLINE_*_LABEL`, `eventLabel`, stage `labelFor`,
  `outcomeCopy`, `requestErrorCopy`, `describeTaskException`, `PRICING_MODEL_COPY`).
- The 13-state agent machine → 7 semantic stages.
- Tool calls / HTTP / latency / model plumbing → a "who did what" narrative
  (`buildActivity` drops everything `looksTechnical`).
- Idempotency keys, session headers, the response envelope → the `apiRequest`
  helper.
- Commitment creation, the handover secret, the audit trail → invisible; the
  buyer sees "your decision is recorded" and a handover code.
- FX conversion math, USDC decimals → `amountUsdcDisplay` (a human number).
- The x402 failure taxonomy → 3–5 buyer-facing `Callout`s.
- Route template selection, the `/v1` endpoint string, slug generation →
  invisible in quick-start.
- Notification event names, dedupe keys, recipient resolution → plain
  title/body.
- Push VAPID / subscription mechanics → two switches.
- The `after()` background-execution trick → invisible; the client just polls.

# 7. Summary — the abstraction posture, in one line each

- **Buyer conversation & agent run:** abstract aggressively; the 7-stage spine +
  narrative + one ✨ label is the right level. Keep the "not saved" label but it
  is slightly misleading (P10).
- **Buyer decision & handoff:** abstract _nothing_. This is the product.
- **MiniPay:** abstracted well at the boundary; keep "network fee", the locked
  rate, the recipient, "Intra never holds it".
- **x402 receipt:** over-exposed (P1). The label + honesty copy is enough; drop
  the chain fields from the buyer view.
- **Supplier quoting:** the highest-frequency friction; the precision is
  crypto-adjacent for the target user (P2).
- **Operator surfaces:** functional but unpolished (P3, P7); they leak enums
  because they were built for a human who can read them, but they're also the
  judge-facing evidence view.
- **Onboarding (quick-start):** abstracted well. **Onboarding (full):** the
  single largest abstraction failure in the product (P5).
- **Freshness, exceptions, Proofline, attestation copy:** exemplary — every one
  answers "what / do I act / what next" in plain language, and the disclaimers
  are verbatim and everywhere.
