# 15 — Redesign Decision Map

> Every redesign decision, traced back to the evidence in the X-ray that
> justifies it. Read this to challenge the brief — if a decision here isn't
> backed by a real finding, it shouldn't be in
> [`13-LOVABLE-REDESIGN-PROMPT.md`](13-LOVABLE-REDESIGN-PROMPT.md).
>
> Structure: **X-ray finding → design decision → why → what changes → what does
> NOT change → risk**.

# Part 1 — UX restructuring decisions

## D1 — `/tasks/:id` becomes a 4-zone focus layout

|                          |                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `04-SCREEN-SPEC.md` S-04: on a `HANDOFF_READY` task with MiniPay the page renders **7–8 stacked panels** (quote card + recommendation card + `PayPanel` + `HandoffCard` + `HandoverCodePanel` + `OrderProblemPanel` + activity + feedback). `09-TASK-COMPLEXITY-AUDIT.md` W3: "cognitive load moderate-to-high… the user must figure out which one is the current action." `10` §16 #4, `02` P-none-specific but implied. |
| **Decision**             | Restructure into 4 zones: **Status · What now (focus card) · Detail (collapsible) · History (collapsed)**. Zone 2 is driven by a `nextAction(view)` function (already proposed in `docs/UX_ARCHITECTURE.md` §3.5).                                                                                                                                                                                                        |
| **Why**                  | The product's own state model always knows the single next action; the UI just doesn't express it. Every other buyer surface (`BuyerWorkPanel`, the agent `OutcomePanel`) already leads with "what now" — the task page is the outlier.                                                                                                                                                                                   |
| **What changes**         | Layout and hierarchy only. Panels that were top-level become: steps inside Zone 2 (`PayPanel`, `HandoverCodePanel`), Zone 2 itself when they outrank (`PriceChangePanel`), a link that opens a sheet (`OrderProblemPanel`), or a collapsed section (x402 receipt, the quote breakdown).                                                                                                                                   |
| **What does NOT change** | Every panel's _content_, every action's _behaviour_, every state transition. `getTaskView` returns the same data. The WhatsApp message still shown in full. The decision still explicit.                                                                                                                                                                                                                                  |
| **Risk**                 | If `nextAction()` mis-classifies a rare state (e.g. a price change _and_ an expired quote), Zone 2 shows the wrong focus. Mitigation: an explicit priority order (price-change > exception > handoff > decision > wait) and a fallback that shows a neutral "here's where this stands" summary.                                                                                                                           |

## D2 — Persistent buyer bottom navigation

|                          |                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `03-COMPONENT-INVENTORY.md` P (navigation), `10` §16 #4/#12: no persistent buyer nav; `/agent` ↔ `/activity` ↔ `/tasks/:id` linked only by in-page pills and back-links; `primaryNav` (`src/lib/site.ts`) lists 7 entries, `Header` renders 3; `/activity` reachable only from the "Activity" pill on `/agent`. `08-MOBILE-PWA-AUDIT.md` §7: "no persistent way to move between home / activity / current task." |
| **Decision**             | Bottom nav (mobile) / left rail (≥ lg): **Home · Activity · Requests**, with a "needs you" badge. On `/tasks/:id` the bar is replaced by that task's sticky primary action + a "‹ back" affordance.                                                                                                                                                                                                              |
| **Why**                  | The buyer has three recurring destinations; they should be one tap apart. A "needs you" count on the bar is the continuity signal for a returning user (`13` PART 11).                                                                                                                                                                                                                                           |
| **What changes**         | Navigation chrome. The in-page "Activity" pill and the "‹ Home" back-link are retired.                                                                                                                                                                                                                                                                                                                           |
| **What does NOT change** | The routes themselves, the content of each destination.                                                                                                                                                                                                                                                                                                                                                          |
| **Risk**                 | A bottom bar competes for vertical space on a 360px screen. Mitigation: `min-h-14` (56px), it hides during full-screen flows (conversation, onboarding), and it's replaced by the sticky action on the task screen.                                                                                                                                                                                              |

## D3 — Merchant quote form: 2 fields + a sheet + "Add detail"

|                          |                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Finding**              | `09` W11: `QuoteResponseForm` has **10 fields** including a `datetime-local` (a 2-step mobile picker), a fixed/range toggle, and a `confidence` low/med/high select. `docs/AGENTIC_ARCHITECTURE.md` §5.3 names quoting "the highest-frequency merchant interaction… most likely to happen on a phone, one-handed, in a noisy shop, mid-job." `02` P2, `10` §16 #6. |
| **Decision**             | Default to **amount + turnaround** in a bottom sheet. Fixed/range → a segmented control. Expiry → an optional chip group ("Holds for: 1 day / 3 days / No limit"). Delivery charge, availability note, assumptions, confidence → behind one "Add detail" disclosure, collapsed.                                                                                    |
| **Why**                  | The common case is "here's my price and how fast." The other fields are real (they're in the schema and the buyer sees them) but they're refinements, not requirements — `submitQuoteRequestSchema` only requires `amountMin` + `turnaround`.                                                                                                                      |
| **What changes**         | Field prominence and input controls.                                                                                                                                                                                                                                                                                                                               |
| **What does NOT change** | The fields still exist and still submit. The buyer still sees fixed-vs-estimate, the expiry, the assumptions when the merchant fills them. The "Intra doesn't independently check these" line stays. `POST /api/routes/:id/quotes` unchanged.                                                                                                                      |
| **Risk**                 | A merchant who wants to set confidence/assumptions has one more tap. Acceptable — they're the minority and the disclosure is one tap.                                                                                                                                                                                                                              |

## D4 — Payment presented as REVIEW → CONFIRM → PAY → VERIFIED

|                          |                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `07-TRUST-MONEY-BLOCKCHAIN-UX.md` §4–6, `09` W4, `02` §3. The MiniPay path is _already well abstracted_ ("network fee", locked rate, no ABI on the default view) — but `PayPanel` is a single card that cycles phases, and the phases aren't presented as a clear sequence. The x402 `PaymentReceipt` on the same screen _does_ leak chain detail (`02` P1, `10` §16 #5). |
| **Decision**             | The order payment becomes an explicit 4-step sheet. The exchange rate + source + lock time move behind "How this is calculated". The x402 fee card is reduced to one honest line on the happy path.                                                                                                                                                                       |
| **Why**                  | "Pay" should feel like a payment ritual the user recognises (review → confirm → pay → done), not a state machine they watch. The chain detail that matters (the rate, the recipient, "confirmed only after verification") stays; the chain detail that doesn't (USDC units, contract, CAIP) goes behind a disclosure or off the buyer view entirely.                      |
| **What changes**         | The presentation of `useOrderPayment`'s phases; the placement of the rate detail; the x402 card's verbosity.                                                                                                                                                                                                                                                              |
| **What does NOT change** | `createOrderPaymentIntent`, `wallet-adapter.payOrder`, `verifyOrderPayment`. The rate is still fetched, locked, and shown with its source. "Confirmed" is still only after a real receipt read. The WhatsApp fallback is still always present. The wallet approval is still a separate human step.                                                                        |
| **Risk**                 | Hiding USDC behind a disclosure could feel like obscuring what's really happening. Mitigation: it's one tap away, always, and labelled clearly ("How this is calculated") — not removed.                                                                                                                                                                                  |

## D5 — Differentiate the two handover codes

|                          |                                                                                                                                                                                                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `00` §20 #8, `10` §16 #5: the buyer's `HandoverCodePanel` code (buyer→merchant, ADR-018) and the merchant's Proofline `pickupCode` (merchant→buyer, ADR-016) both render as "a large mono code in a bordered box" on related surfaces with similar copy. |
| **Decision**             | Label and style them by **direction**: buyer's = "Your collection code — show this to the business"; merchant's = "Give this code to the customer". Distinct container/accent for each.                                                                  |
| **Why**                  | They are genuinely different mechanisms serving different halves of a two-party protocol. The user (on either side) needs to know which code they _show_ vs which they _receive_.                                                                        |
| **What changes**         | Copy and visual container.                                                                                                                                                                                                                               |
| **What does NOT change** | Both mechanisms, both flows (`proofline/confirm-pickup`, `handover/sign-request` + `submit`). The commit-reveal, the EIP-712 signing — all unchanged and still hidden.                                                                                   |
| **Risk**                 | Minimal. This is a clarity fix.                                                                                                                                                                                                                          |

## D6 — Fold or drop `/request`

|                          |                                                                                                                                                                                                                                                                                  |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `00` §20 #2 (corrected): `/request` + `RequestForm` are **not linked from anywhere** — both landing CTAs and the PWA `start_url` point at `/agent`. Live, tested, non-deprecated code. `10` §21 unknown: "whether `/request` is intentionally retired or accidentally orphaned." |
| **Decision**             | The redesign uses `/agent` as the single buyer entry. If a form path is still wanted, surface it as a "prefer a form?" affordance _inside_ `/agent` that pre-fills the conversation. Do not maintain two parallel routes with different capabilities.                            |
| **Why**                  | Two entry points that produce differently-shaped tasks (`buyerClaimSession` set vs not; multi-provider vs single-route) is a maintenance and comprehension cost with no user benefit — nobody can reach the second one anyway.                                                   |
| **What changes**         | One buyer entry instead of two (one of which is unreachable).                                                                                                                                                                                                                    |
| **What does NOT change** | The underlying `POST /api/tasks` + `submit` flow still exists (the agent run uses the same primitives).                                                                                                                                                                          |
| **Risk**                 | If `/request` was deliberately kept for a reason not in the repo, this is wrong. Flagged as an **unknown** — the redesign should confirm with the product owner. Default: fold into `/agent`.                                                                                    |

## D7 — One-screen onboarding is the only onboarding

|                          |                                                                                                                                                                                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `01` J16, `09` W10, `02` P5, `10` §16 #2, `docs/UX_ARCHITECTURE.md` F1: `OnboardingForm` (`/supplier/onboard/full`) collects 15 fields then calls `setDraft(...)` and **nothing else** — no POST. It tells the merchant to "email this JSON to an operator." `QuickStartForm` (`/supplier/onboard`) _does_ persist. |
| **Decision**             | The redesign builds only the one-screen (`QuickStartForm`) path. The detailed form is treated as operator-internal / out of scope.                                                                                                                                                                                  |
| **Why**                  | The full form is the product's single worst load-to-outcome ratio (`09` W10). Fixing its persistence is a _backend_ change the redesign is forbidden from making. The one-screen path already covers the common case and works end-to-end.                                                                          |
| **What changes**         | The redesign doesn't ship a redesigned `/supplier/onboard/full`.                                                                                                                                                                                                                                                    |
| **What does NOT change** | The detailed form's route/code can stay for operators; the redesign just doesn't invest in it. Quick-start behaviour unchanged.                                                                                                                                                                                     |
| **Risk**                 | The full form collects richer Capability Card data (service area, hours, turnaround) that quick-start skips. If that data matters for the pilot, this is a product decision to escalate — not a redesign decision.                                                                                                  |

## D8 — Re-word the "Demo only — nothing here is saved" label

|                          |                                                                                                                                                                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `06-COPY-INFORMATION-ARCHITECTURE.md` §3, `02` P10, `09` W1: the label is on the conversation, but the task/quote/decision/commitment a run produces **are** persisted. A first-time user could read it as "this doesn't do anything real." |
| **Decision**             | Re-word to something true: _"This chat isn't saved — but your requests are."_ Keep a "not saved" concept for the _agent run store_ (30-min TTL) where it's accurate.                                                                        |
| **Why**                  | `CLAUDE.md` §4.4 requires demo/non-persistent state to be labelled — but the label must be _accurate_. The current one over-claims and undermines trust in the outcome.                                                                     |
| **What changes**         | Copy.                                                                                                                                                                                                                                       |
| **What does NOT change** | The conversation transcript genuinely isn't persisted; the agent run store genuinely has a TTL. Those facts stay labelled, just precisely.                                                                                                  |
| **Risk**                 | None. Accuracy improvement.                                                                                                                                                                                                                 |

# Part 2 — Design system decisions

## D9 — Preserve-and-refine (not rebuild)

|                          |                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `12-DESIGN-SYSTEM-RECOMMENDATION.md` §1: the core principles (light-first, flat, hairline, tint elevation, one action colour, status = icon + word, no web font for body, reduced-motion, mobile-first, 360px) are "exactly right for the audience." The execution has real gaps (stale green in 4 places, a mismatched cold `primary-wash`, ad-hoc tint usage, missing brand). |
| **Decision**             | Option **B — preserve and refine.** Keep every principle; consolidate colour _roles_; fix the stale surfaces; add the missing brand + illustrations.                                                                                                                                                                                                                            |
| **Why**                  | A ground-up rebuild throws away the hardest-won parts (the accessible-status vocabulary, the honesty-`Callout` pattern, the reduced-motion discipline). The foundation is genuinely good — `ADR-009`/`ADR-022` did the thinking.                                                                                                                                                |
| **What changes**         | Palette execution, colour-role naming, typography decision, two structural layouts, the asset set.                                                                                                                                                                                                                                                                              |
| **What does NOT change** | The token architecture (CSS custom properties → Tailwind mapping), light-only, flat/no-shadow, the component vocabulary (`Callout`, `StatusPill`, `DataList`), lucide as the icon system, no web font for body/UI.                                                                                                                                                              |
| **Risk**                 | "Refine" can drift into "rebuild" during implementation. Mitigation: the token file shape in `12` §18 is the contract — new roles, same structure.                                                                                                                                                                                                                              |

## D10 — The `neutral`/"honest" status tone is load-bearing

|                          |                                                                                                                                                                                                                                                                                        |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `07` §13 (the trust-copy inventory), `06` §14, `02` §5. The product's honesty statements ("Intra never fabricates a payment", "no receipt exists", "operational evidence, not proof", "Demo — not saved", "stale") currently use the `Callout tone="unavailable"` (grey on `surface`). |
| **Decision**             | Formalise this as the **`neutral`** status role: grey text on warm sand, a `CircleSlash`/`Info` icon, **calm and matter-of-fact — never like an error.** It is the visual voice of "here is what is NOT happening / NOT verified / NOT real."                                          |
| **Why**                  | These moments are the product's trust differentiator (`PRODUCT_VISION.md` §3.1 property 5: "Honest about payment"). If they read as errors, the honesty becomes alarming; if they read as calm facts, the honesty becomes reassuring.                                                  |
| **What changes**         | The tone gets a name and a consistent spec; it's applied everywhere an honesty statement appears.                                                                                                                                                                                      |
| **What does NOT change** | Every honesty phrase (`07` §13) stays verbatim at its current moment.                                                                                                                                                                                                                  |
| **Risk**                 | Overusing `neutral` dilutes it. Mitigation: it's reserved for "what is NOT happening" — not for general secondary content (that's `text-subtle`).                                                                                                                                      |

## D11 — Resolve the typography question (self-hosted display face, `font-display: optional`)

|                          |                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `11-ASSET-INVENTORY.md` §1, `12` §3: `<h1–h3>` are `font-serif` weight 300; the stack is `"Iowan Old Style", Palatino, Georgia, ui-serif`; the primary audience is on **Android → they see Georgia** (and weight 300 of Georgia is faux-light). `ADR-009`/`ADR-022` forbid a web-font fetch (data cost).                                                      |
| **Decision**             | Add **one** self-hosted, subset (~≤ 25KB WOFF2), `font-display: optional` display face for headings only. Body/UI/mono stay on system stacks. Requires a one-line ADR amendment. Fallback: if rejected, design headings for Georgia at weight **400** (not 300). Do **not** go all-sans.                                                                      |
| **Why**                  | `font-display: optional` means the face is used only if it's cached or loads in ~100ms — otherwise the system serif is used and never swaps. Zero CLS, zero render-block, ~20KB one-time. The "editorial" identity is a real brand asset that currently doesn't exist on the target device. All-sans reads generic (the brief explicitly warns against this). |
| **What changes**         | One `@font-face`, one file in `public/fonts/`, the heading font stack.                                                                                                                                                                                                                                                                                        |
| **What does NOT change** | Body, UI, and mono text — all still system stacks, still zero fetch. The `no-web-font` rule for _those_ holds.                                                                                                                                                                                                                                                |
| **Risk**                 | Breaks the letter of two ADRs. Mitigation: the amendment is narrow and the `optional` loading strategy honours the _intent_ (never cost the user data on a slow connection, never block render). Escalate as a product decision.                                                                                                                              |

## D12 — No dark mode, no charts, no dashboard

|                  |                                                                                                                                                                                                          |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**      | `ADR-009`/`ADR-022`: light-first is deliberate (daylight use, cheap screens). `00` §1, `PRODUCT_VISION.md`: "not a dashboard." `13` PART 15.                                                             |
| **Decision**     | Light theme only. The only tables are the two existing simple ones (`/evidence` targets-vs-actual, `/operator` metrics). No KPI tiles, no charts, no data grid.                                          |
| **Why**          | The audience and the product both argue against it. A dark mode doubles the token surface for a user base that uses the app outdoors. A dashboard framing fights the "human commerce workflow" identity. |
| **What changes** | Nothing — this is a "keep the existing decision" entry, stated so the redesign doesn't drift.                                                                                                            |
| **Risk**         | None.                                                                                                                                                                                                    |

# Part 3 — Complexity-abstraction decisions

## D13 — Move x402/chain detail off every buyer surface

|                          |                                                                                                                                                                                                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `02` P1, `07` §8, `09` W3, `10` §16 #5: the x402 `PaymentReceipt` on `/tasks/:id` shows `attributionTag` (raw `celo_…`), `amountAtomic / 1e6` inline, CAIP-2 network ids, "via agent payment protocol" — on a buyer surface, for a payment that is **almost always `UNAVAILABLE`**. |
| **Decision**             | On the buyer's task screen, the agent-query-fee is at most **one honest line** ("No agent query fee — this came through the web."). Any real detail (only on the rare `SETTLED` path) moves to the operator evidence view.                                                          |
| **Why**                  | This fee is not the buyer's money, is capped at $0.05, and is a different thing from the order price (`BR-004`). The chain fields serve nobody on the buyer surface.                                                                                                                |
| **What changes**         | The x402 card's verbosity on `/tasks/:id`.                                                                                                                                                                                                                                          |
| **What does NOT change** | The x402 flow itself, the `service_payments` records, the operator trace, the `/docs` explanation. The honesty ("Intra never fabricates a payment") stays.                                                                                                                          |
| **Risk**                 | Minimal — this removes noise, not signal.                                                                                                                                                                                                                                           |

## D14 — Keep the AI presented as a progress spine + narrative, not a character

|                          |                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `02` §2, `12-COMPLEXITY` (doc 02) §2, `05` §2.3: the model "sits above the deterministic orchestration, never inside it… proposes, `runBuyerAgent` disposes." The UI already does this well — a 7-stage spine, a "who did what" narrative, one "✨ agent's reasoning" label. The conversational classifier is _deterministic_ (`classifyMessage`). |
| **Decision**             | Preserve. The AI is a progress sequence and a narrative. **No chatbot avatar, no "thinking" shimmer, no AI mascot.** The chat copy should not over-promise "AI understanding" (the reading is rules).                                                                                                                                              |
| **Why**                  | The existing treatment is the right level of abstraction (`10` §12). A character or a shimmer would make the user think about the model — exactly what the brief forbids.                                                                                                                                                                          |
| **What changes**         | Nothing structural; the copy on the conversation intro may soften "I'll find a business…" claims.                                                                                                                                                                                                                                                  |
| **What does NOT change** | The stage spine, the narrative, the ✨ label, the "what I can't confirm" section.                                                                                                                                                                                                                                                                  |
| **Risk**                 | None.                                                                                                                                                                                                                                                                                                                                              |

## D15 — Humanise the WhatsApp message

|                          |                                                                                                                                                                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Finding**              | `06` §4.8, `09` W3, `10` §16 #14: `buildOrderMessage` outputs raw brief keys (`- size: A5`, `- colour: full-colour`) in the message a real person reads in WhatsApp — the one place the buyer sees un-humanised data. |
| **Decision**             | The pre-filled message uses the same humanised labels the rest of the UI uses ("Paper size: A5", "Colour: Full colour", "Needed by: Friday 3pm").                                                                     |
| **Why**                  | It's the buyer's voice to the business; it should read like a person wrote it, and match everything else in the app.                                                                                                  |
| **What changes**         | The message template's field formatting (a copy/formatting change, not a logic change).                                                                                                                               |
| **What does NOT change** | The message is still generated, still shown in full, still never auto-sent, still ends with "so I can approve the order."                                                                                             |
| **Risk**                 | None.                                                                                                                                                                                                                 |

# Part 5 — Final review (challenging the brief)

The instructions require self-challenge. Here is the honest assessment against
each question:

| Question                                                                                         | Answer                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Are we simplifying the UX or just making it prettier?**                                        | Simplifying, in three concrete places: `/tasks/:id` (7–8 panels → 1 focus card), the quote form (10 fields → 2 + a disclosure), and payment (a phase-cycling card → a recognisable 4-step ritual). The design-system work (palette, brand, illustrations) is refinement — it improves coherence and trust, not task speed. Both are justified; they're not conflated.                                              |
| **Does every important screen have a clear primary action?**                                     | This is now a **hard success criterion** (`13` PART 21 #2). The 4-zone task layout, the sticky bottom action, and the `nextAction()` helper all exist to guarantee it. The one screen where it's genuinely ambiguous today — `/tasks/:id` — is the #1 restructure.                                                                                                                                                 |
| **Can a first-time user understand what's happening without knowing crypto?**                    | Yes, if the abstraction rules in `13` PART 13 hold: "MiniPay" = a payment method with a logo; "network fee" not "gas"; USDC + rate behind "How this is calculated"; no contract/chain/CAIP/atomic units anywhere on the happy path; the handover code framed as "a code you show"; the attestation framed as "both sides confirmed". The existing MiniPay abstraction (`02` §3) already proves this is achievable. |
| **Can a merchant complete the common workflow quickly on a phone?**                              | Target: send a price in < 20s, one-handed (`13` PART 21 #3). The 2-field quote sheet + sticky action + segmented controls are aimed exactly at `AGENTIC_ARCHITECTURE.md` §5.3's finding.                                                                                                                                                                                                                           |
| **Can a buyer understand payment without understanding blockchain?**                             | Yes — REVIEW → CONFIRM → PAY → VERIFIED, with the chain reality one disclosure-tap away, never hidden entirely (that would be deceptive), never on the summary (that would be noise).                                                                                                                                                                                                                              |
| **Can the user recover naturally from interruption?**                                            | The 5-bucket work list + resumable task screen + deep-linking notifications + the "here's what changed" highlight already give this. The redesign strengthens it with the persistent bottom-nav "needs you" badge. The one unrecoverable case (device switch) is a **backend limitation the redesign is not allowed to fix** — it can only make "save this link" prominent.                                        |
| **Does the interface communicate trust without exposing implementation?**                        | The trust model (`13` PART 12) is: the full deal on the surface at the decision, "who you pay, directly", verification before "confirmed", the money line on every failure, the calm `neutral` tone for honesty statements, `/evidence` separating real from demo. None of that requires a hash, a schema id, or a token unit.                                                                                     |
| **Are we preserving the strongest existing UX patterns?**                                        | `13` PART 18 lists 14 non-negotiables. The strongest — `describeTaskException`, the "who did what" narrative, consequence-named buttons, plain-language status labels, honest empty states, the `Callout` vocabulary — are explicitly "re-style, don't remove."                                                                                                                                                    |
| **Are we fixing the actual weaknesses from the X-ray?**                                          | `13` PART 19 has 13 fixes, each mapped to a numbered X-ray finding (`10` §16). No invented problems.                                                                                                                                                                                                                                                                                                               |
| **Are we adding visual assets because they help comprehension, or just because they look nice?** | The 8 illustrations (`11` §3.2, `14` §2) are pinned to 8 specific trust/status moments and forbidden everywhere else.
