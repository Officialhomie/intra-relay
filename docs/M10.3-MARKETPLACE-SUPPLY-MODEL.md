# M10.3 — Marketplace supply model audit

**Goal, in one sentence**: establish whether Intra's existing schema and services
can represent ONE supplier network spanning many categories, or whether we are
accidentally building a printing-only vertical.

**Status**: audit only. No code, schema, migration, or discovery change was made.

**Headline finding**: the conceptual model `BUSINESS → CATEGORY → SERVICE →
ROUTE` is **already ~80% implemented** and needs **no new tables**. The route is
already the unit of discovery, a business can already hold routes from any
category, and capability data already has exactly one source. The real gaps are
in the **onboarding mapping** (which hardcodes one category and discards the
service list it already collects) and in **route-level commercial attributes**
that are collected but never persisted.

**Second headline finding (added on re-audit)**: Intra currently runs **two
independent, unreconciled category vocabularies** — one on the demand side
(`intent/domain.ts`) and one on the supply side (`businesses/schema.ts`). They
agree on only three of eight values, are not linked by any shared type, and the
mismatch is already load-bearing: a supplier can onboard as `catering`, but the
buyer conversation layer can never emit `catering` (it emits `food`), so that
supply would be structurally undiscoverable through the main buyer entry point.
This is the finding most directly threatening "one marketplace, many
categories", and it costs nothing to fix now versus later. See §2.1 and G8.

---

## 1. Current architecture

Four layers, only two of which are tables:

| Concept            | Where it lives                                   | Kind                |
| ------------------ | ------------------------------------------------ | ------------------- |
| Business           | `businesses` table                               | Database row        |
| Category           | `businesses.category` enum column                | Database column     |
| Service            | `SERVICE_TEMPLATES` in `routes/templates.ts`     | **Code constant**   |
| Route              | `quote_routes` table                             | Database row        |
| Capability profile | `buildBusinessCapabilities()` in `capability.ts` | Derived, no storage |
| Discovery          | `GET /api/routes/active?routeSlug=`              | Query, no storage   |

There is **no `services` table**. "Service" exists as a versioned code catalogue
of five `ServiceTemplate` entries. A route is an _instance_ of a template, bound
to one business.

## 2. Business / category / service / route relationships

```
businesses (1) ──< quote_routes (N)        unique on (business_id, slug)
     │                    │
     │ category           │ slug === ServiceTemplate.id
     ▼                    ▼
business_category    SERVICE_TEMPLATES  (code, 5 entries, 1 per category)
  enum (5 values)         │
                          └── category: BusinessCategory
```

- A business has **exactly one** `category` (NOT NULL enum).
- A business may have **many** routes — uniqueness is `(businessId, slug)`.
- A route has **no category column**. Its category is implied by its template.
- A route's `slug` **is** its template id (`route.slug = template.id`,
  `routes/service.ts`), so route slugs are stable service identifiers shared
  across businesses.

The template catalogue (`routes/templates.ts`):

| Template id             | Category | Availability  | Default pricing  |
| ----------------------- | -------- | ------------- | ---------------- |
| `flyer-printing`        | printing | **mvp**       | `STARTING_FROM`  |
| `graphic-design-quote`  | design   | `coming_soon` | `QUOTE_REQUIRED` |
| `event-catering-quote`  | catering | `coming_soon` | `STARTING_FROM`  |
| `local-delivery-quote`  | delivery | `coming_soon` | `FIXED`          |
| `service-request-quote` | other    | `coming_soon` | `QUOTE_REQUIRED` |

`getTemplateForCategory()` is **1:1** — it returns the _first_ template matching
a category, falling back to `SERVICE_TEMPLATES[4]` ("other"). This is the single
structural constraint that blocks a category from holding multiple services.

### 2.1 Two category vocabularies (the demand/supply split)

Category is defined **twice**, in two places that never reference each other:

| Side       | Source of truth                                  | Type                                | Values                                                            |
| ---------- | ------------------------------------------------ | ----------------------------------- | ----------------------------------------------------------------- |
| **Supply** | `BUSINESS_CATEGORIES` (`businesses/schema.ts`)   | const tuple → zod enum → **pgEnum** | `printing`, `design`, `catering`, `delivery`, `other`             |
| **Demand** | `DomainCapability.category` (`intent/domain.ts`) | plain **`string`**                  | `printing`, `food`, `electronics`, `design`, `delivery`, `repair` |

```
         demand-only            shared             supply-only
   food, electronics, repair   printing          catering, other
                               design
                               delivery
```

Consequences, all verified in code:

- **`catering` supply is unreachable.** `event-catering-quote` exists, a business
  can be `catering`, but no buyer message can ever classify to `catering` — the
  intent layer's nearest concept is `food`, which is a different string and
  resolves to nothing on the supply side.
- **`food`, `electronics`, `repair` demand is unresolvable.** Those three intent
  domains have no `BusinessCategory` and no `ServiceTemplate`, so they can never
  route to supply even if a willing supplier onboarded.
- **Nothing type-checks the relationship.** `DomainCapability.category` is
  `string`, not `BusinessCategory`, so the two lists can drift silently. They
  already have.
- **The bridge is a single hardcoded link.** `DomainCapability.routeSlug` is the
  one demand→supply join, and it is non-null for exactly one domain:
  `printing → flyer-printing`. Every other domain has `routeSlug: null`.
- **Liveness is tracked twice.** `DomainCapability.serviceable` (demand) and
  `ServiceTemplate.availability: "mvp" | "coming_soon"` (supply) are independent
  booleans about the same question, kept in sync only by hand.

Today this is masked because exactly one category (printing) is live on both
sides. It becomes a correctness bug the moment a second category launches.

## 3. Current database representation

**`businesses`** — identity, contact, `category`, `city`, `country`,
`payoutAddress`, `quoteCurrency`, `manageToken`, `consentAt`,
`verifiedByOperatorAt`/`Label`, `status`.

**`quote_routes`** — `businessId` FK, `slug`, `name`, `description`,
`inputSchema` (jsonb), `queryFeeUsd`, `responseSlaMinutes`, `quoteCurrency`,
`pricingModel`, `priceAmount`, `priceUnit`, `payoutAddress`, `endpoint`,
`status`, `priceUpdatedAt`, `verifiedAt`, `activationChecklist` (jsonb).

**Not persisted anywhere** — despite being collected by Tally: service area,
turnaround (as a route attribute), minimum order, fulfilment (pickup/delivery),
operating hours, availability windows. These survive only inside
`onboarding_submissions.normalizedData` jsonb and are never promoted into the
domain model.

Note: `quotes.turnaround` exists, but that is the turnaround a merchant states
**on a specific quote**, not a property of the service.

## 4. Current discovery flow

`GET /api/routes/active?routeSlug=<slug>` (default `flyer-printing`):

```sql
SELECT route.*, business.slug, business.name, business.city, business.country
FROM quote_routes
INNER JOIN businesses ON quote_routes.business_id = businesses.id
WHERE quote_routes.slug = :routeSlug
  AND quote_routes.status = 'ACTIVE'
```

- **The match criterion is route slug + ACTIVE. Nothing else.**
- **Category is not in the query** — not filtered, not selected.
- `city`/`country` are **selected for display but never filtered on**.
- Buyer-side, `discoverProviders` (`agent/tools/registry.ts`) takes a single
  input: `{ routeSlug }`. Quantity, location, deadline, and budget are applied
  **after** discovery by the policy layer, not during it.

This already matches the target model: **the service/route drives commercial
discovery; the business's category does not participate.**

## 5. Current supplier profile flow

One surface, `/supplier/[slug]`, gated by `?t=<manageToken>` (ADR-008):

- **With the token**: action centre, in-flight counts, own performance record,
  editable published price, editable basic details (4 fields, M10.2),
  `AgentProfilePreview`, notification settings.
- **Without it**: degrades to a read-only stub — header, nav, services list, and
  a "Read-only view" callout.
- `/supplier/[slug]/review` adds business details (read-only: contact channel,
  currency, payout address, consent, verification state) and capability routes.

**There is no public, human-facing business profile.** `src/app/business/` does
not exist. The management page is the only business-facing surface, and it is
not designed or authorised to be a buyer-facing one.

## 6. Current agent capability flow

`GET /v1/[businessSlug]/capabilities` → `buildBusinessCapabilities()`:

```
{ version, business: { slug, name, category, location, operatorVerified },
  routes: RouteCapability[], finalOrderPolicy, generatedAt }
```

- Returns **all** of a business's routes, each with an explicit
  `availability: { state, acceptingQuoteRequests, reason, detail }` rather than
  a silently filtered list.
- Practises data minimisation: `orderContact` is attached **only** to a route
  that is actually usable right now.
- Versioned by `CAPABILITY_CONTRACT_VERSION`.
- Derives entirely from `businesses` + `quote_routes` — **no separate store**.
- M10.2's `AgentProfilePreview` renders this same function, explicitly so the
  supplier's view cannot drift from the agent's.

This is a sound agent-facing representation and should be preserved as the
canonical capability source.

## 7. Current operator organization

Flat and route-centric. `listOperatorQueue()` (`routes/reads.ts`):

```sql
SELECT route.*, business.*
FROM quote_routes INNER JOIN businesses ...
WHERE quote_routes.status IN ('DRAFT','PENDING_VERIFICATION','ACTIVE','PAUSED')
ORDER BY quote_routes.updated_at DESC
```

- One row **per route**, not per business. A business with three routes appears
  three times.
- **No category grouping anywhere** — zero `category` references in any operator
  component.
- Tally submissions are listed separately via `/api/operator/onboarding`,
  primarily so `NEEDS_REVIEW` submissions (which create nothing) have a home.

Route-centricity is correct and consistent with the target model. The absence of
a category or business-grouped view is a gap that only bites once supply is
genuinely multi-service.

## 8. Gaps

**G1 — Tally hardcodes the category.** `createBusinessFromOnboarding()` sets
`category: "printing"` as a literal, alongside `country: "Nigeria"`,
`quoteCurrency: "NGN"`, `contactChannelType: "whatsapp"`. Every remotely
onboarded business is a printing business regardless of what it does.

**G2 — Tally collects a service list and discards it.** `NormalizedOnboarding`
carries `services: NormalizedService[]` (one of 14 named services, or free
text, each with `pricingModel`, `priceText`, `notes`). That array is used
**only** for validation (must be non-empty) and an analytics `service_count`.
Route creation then ignores it entirely: `createRoute(db, business.slug, {})`
builds exactly one route from the category default. **This is the single
biggest modelling gap — the form already asks the multi-service question the
model wants answered, and the answer is thrown away.**

**G3 — one service per category, and 13 of the 14 collected services have no
template at all.** `getTemplateForCategory()` returns a single template, so
"printing" cannot mean flyers _and_ banners _and_ business cards. Worth being
precise about the scale of this, because it changes how G2 can be fixed: the 14
`SERVICE_LABELS` the Tally form collects (business cards, flyers, posters,
banners, stickers, brochures, booklets, invitations, apparel, packaging, labels,
large-format, signage, documents) are **all printing sub-services** — they do
not span categories. Only `flyers` has a template. So "map `services[]` → template
ids" (§10.2) cannot be executed as a pure mapping today; it first requires a
design decision (see §10.2).

**G4 — route-level commercial attributes are not persisted.** Service area,
turnaround, minimum order, fulfilment, availability — collected by Tally,
stranded in `normalizedData` jsonb. Service area is the most consequential,
because discovery cannot filter on what it cannot read (see also the
location-precision problem: `deliveryArea` is collected from buyers and never
used for matching).

**G5 — no public human-facing business profile.**

**G6 — no category index over live supply.** Nothing aggregates "which
businesses/routes exist in printing."

**G7 — catalogue is nominally multi-category, operationally single-category.**
Four of five templates are `coming_soon`.

**G8 — two unreconciled category vocabularies (see §2.1).** Demand
(`intent/domain.ts`: printing, food, electronics, design, delivery, repair) and
supply (`BUSINESS_CATEGORIES`: printing, design, catering, delivery, other)
overlap on only three values, are joined by no shared type, and already
disagree in ways that would strand real supply (`catering`) and real demand
(`food`, `electronics`, `repair`). This is the gap that most directly
contradicts the "one marketplace" goal, and it is the cheapest one to close
while only one category is live.

## 9. Recommended canonical model

Keep two tables. Change where category _lives conceptually_, not where it is
stored.

```
BUSINESS   = businesses row                        (who are you)
CATEGORY   = ServiceTemplate.category              (what market)  ← derived
SERVICE    = ServiceTemplate  (code catalogue)     (what you offer)
ROUTE      = quote_routes row                      (what can be requested)
```

Three principles:

1. **Category becomes derived, not declared.** A business's categories are
   `distinct(templateFor(route.slug).category)` across its routes. Keep
   `businesses.category` as a _primary/default_ hint for onboarding — it already
   only serves as the default template selector — but stop treating it as the
   truth about what a business sells.

2. **Service stays code, not a table.** A route's `inputSchema` is an API
   contract agents depend on. Making services operator-authored rows would let
   supply edit the contract that buyer agents rely on. The template catalogue
   should be versioned with the app.

3. **Route remains the only unit of discovery.** It already is. Category is
   organizational metadata and must stay out of the discovery query.

4. **One category vocabulary, shared by both sides.** There must be exactly one
   list of category identifiers, imported by both `intent/domain.ts` and
   `businesses/schema.ts`, with `DomainCapability.category` typed as
   `BusinessCategory` rather than `string` so drift becomes a compile error
   instead of silently unreachable supply. The demand side keeps its own
   _aliases_ and buyer-facing copy — those are presentation, and they should
   stay where they are; it is the **identifier** that must be shared. Where the
   two lists currently disagree, supply-side naming should generally win for the
   identifier (it is a pgEnum, so changing it costs a migration), with the
   demand side keeping "food" as a human-facing alias of a `catering`-or-renamed
   identifier. That naming call is a decision for the implementing milestone,
   not something to settle here.

## 10. Smallest changes required

Ordered by leverage, **for a later milestone** — none are done here.

1. **Relax `getTemplateForCategory` 1:1 → `getTemplatesForCategory` (many)**,
   retaining a `defaultTemplateFor(category)` for the single-route path.
   Unblocks G3 with no schema change.
2. **Stop discarding Tally `services[]`** instead of hardcoding `"printing"`,
   and create **N draft routes** rather than one. Still `DRAFT`, still
   operator-activated — the verification gate is untouched. Closes G1+G2 and
   needs no new tables. **But note the fork first (G3):** all 14 collected
   services are printing sub-services and 13 have no template, so this is not a
   pure mapping. Two honest options:
   - **(a) Author ~13 new `ServiceTemplate`s**, one per printing sub-service,
     each with its own agent-facing `inputSchema`. Most faithful to "route =
     what exactly can be requested", but it is 13 new API contracts to design,
     version and maintain — and a banner brief genuinely differs from a
     business-card brief, so they cannot share one schema honestly.
   - **(b) One parameterised print-job template** with a `productType` field
     drawn from the 14 labels. Far cheaper, keeps one contract, but weakens
     route-as-unit-of-discovery: an agent can no longer discover "who prints
     banners" without reading every printer's quote inputs.
     Recommendation: **(b) first**, because it closes G1+G2 immediately with one
     template and no contract sprawl, and promote individual sub-services to
     their own templates in (a) only where discovery demand actually proves it.
     This ordering is reversible; the opposite is not.
3. **Derive categories for display/index** from a business's routes. Closes G6
   with a query, not a column.
4. **Add route-level commercial columns only where a consumer will read them** —
   `serviceArea` first, because discovery and eligibility genuinely need it.
   Turnaround and minimum order can stay on the quote until something reads
   them. Partially closes G4; this is the only item needing a migration.
5. **`/business/[slug]` public profile** rendering `buildBusinessCapabilities()`
   filtered to `AVAILABLE` routes plus published pricing. Closes G5 with no new
   source of truth.
6. **Promote templates from `coming_soon` to `mvp`** as each is genuinely
   exercised. Closes G7 operationally, not structurally.

7. **Unify the two category vocabularies (G8).** Export one identifier list,
   import it on both sides, and retype `DomainCapability.category` as
   `BusinessCategory`. No new table; a pgEnum change only if an identifier is
   renamed. Cheap today (one live category, one real supplier cohort),
   progressively more expensive per category launched, and it is the only item
   on this list whose cost grows with delay rather than staying flat.

## 11. What should NOT be changed

- **Route as the unit of discovery.** Already correct.
- **`/api/routes/active` match semantics** (`slug` + `ACTIVE`). Adding category
  to this query would be a regression toward vertical silos.
- **`buildBusinessCapabilities()` as the single capability source.** Any public
  profile must derive from it, never re-implement it.
- **The operator activation gate and its six-item checklist.** Out of scope
  here; strengthening it is a separate concern.
- **`quotes` as the only commitment (BR-003).** Published route pricing stays
  indicative.
- **Do not add a `services` table.** See §9 principle 2.
- **Do not remove `businesses.category`** — demote it to a default, don't drop
  it. It is NOT NULL and feeds the existing onboarding path.
- **Do not "fix" G8 by adding the missing categories to the supply enum.**
  Adding `food`/`electronics`/`repair` as `BusinessCategory` values without
  templates or suppliers behind them manufactures categories Intra cannot
  serve, which is the fabrication rule (CLAUDE.md §4.1) in marketplace form. The
  fix is one shared vocabulary, not a longer one.
- **Do not let the demand side's buyer-facing aliases become identifiers.** The
  aliases in `intent/domain.ts` ("jollof", "hungry", "cakes") are deliberately
  informal and Nigeria-specific. They are good copy and bad primary keys.
- **Capability contract version** — bump `CAPABILITY_CONTRACT_VERSION` if the
  document shape changes.

## 12. Recommended next milestone

> Numbering note: this audit originally proposed "M10.4" for the work below.
> **M10.4 has since been used** for the stateful conversational buyer engine
> (ADR-025). The milestone below is therefore proposed as **M10.6**.

**M10.6 — one vocabulary, then multi-service onboarding.** Scope: §10 items
**7, 1, and 2(b)**, in that order.

Rationale for that ordering — it differs from this document's original
recommendation, which put multi-service onboarding first:

1. **Item 7 (unify the vocabulary) goes first** because it is the only item
   whose cost grows with delay. Every category launched on top of two
   unreconciled lists is another migration and another set of stranded
   suppliers later. It is also small: one shared export and one type change.
2. **Item 1 (relax the 1:1 template lookup)** is the structural unblock, and is
   meaningless before the vocabulary is settled.
3. **Item 2(b) (parameterised print-job route, services no longer discarded)**
   then converts data the system **already collects and currently discards**
   into real routes, with no migration, no discovery change, and the
   verification gate untouched.

Explicitly deferred: the public profile (§10.5), service-area persistence and
location-aware discovery (§10.4), per-sub-service templates (§10.2a), and
category management UI.

## Appendix — the fourteen audit questions

| #   | Question                                                | Answer                                                                                                                                                                                                                     |
| --- | ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Can one business offer services in multiple categories? | **Structurally yes, in practice no.** `createRoute` accepts any `templateId`; nothing enforces category/route agreement. But no path exercises it.                                                                         |
| 2   | Is category on business, service, or route?             | **Business** (`businesses.category`, NOT NULL enum). Routes have no category column; templates do, in code. Note there is also a **second, separate** category list on the demand side (`intent/domain.ts`) — see §2.1/G8. |
| 3   | Can one business have multiple routes?                  | **Yes.** Unique on `(businessId, slug)` — unlimited distinct slugs.                                                                                                                                                        |
| 4   | Is route the correct unit of discovery?                 | **Yes, and it already is.**                                                                                                                                                                                                |
| 5   | Can different businesses offer the same route?          | **Yes.** Uniqueness is per-business, so `flyer-printing` exists on N businesses — this is what enables multi-supplier comparison.                                                                                          |
| 6   | How does `discoverProviders()` match?                   | **`routeSlug` + `status = 'ACTIVE'` only.** No location, category, quantity, or price. Eligibility is applied after discovery.                                                                                             |
| 7   | Canonical pricing source?                               | Two-tier: `quote_routes` published pricing = indicative guidance; the `quotes` row = the only commitment (BR-003).                                                                                                         |
| 8   | Canonical capability source?                            | `buildBusinessCapabilities()`, versioned, derived from `businesses` + `quote_routes`. No separate store.                                                                                                                   |
| 9   | Is `/v1/[slug]/capabilities` suitable?                  | **Yes.** Versioned, availability-aware, minimises merchant data. It is per-business; cross-business discovery is `/api/routes/active`.                                                                                     |
| 10  | Public human-facing profile?                            | **No.** `src/app/business/` does not exist. `/supplier/[slug]` is a management page that degrades to a stub without a token.                                                                                               |
| 11  | Can a supplier see what an agent sees?                  | **Yes**, since `0927301` — `AgentProfilePreview` renders the same capability document.                                                                                                                                     |
| 12  | What is operator-only?                                  | Activation, resuming a pause, all transitions except supplier `→PAUSED` and `DRAFT→PENDING_VERIFICATION`, verification stamps, adding routes, payout address, consent, slug, manage token, the submission queue.           |
| 13  | How is supply listed for operators?                     | **Flat, route-centric queue** ordered by `updatedAt`. No category grouping anywhere.                                                                                                                                       |
| 14  | Is there a category/vertical index?                     | **In code only, and there are two of them** — `SERVICE_TEMPLATES` (supply, 1:1 category→service) and the `intent/domain.ts` registry (demand). Neither indexes _live supply_ by category, and they disagree (§2.1).        |
