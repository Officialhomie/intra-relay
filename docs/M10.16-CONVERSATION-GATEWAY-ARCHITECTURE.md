# M10.16 — Conversation gateway architecture

## Current architecture

The buyer Web client posts directly to `POST /api/conversation`. The route
resolves the opaque per-device buyer session, loads open buyer work, calls
`handleConversationTurn`, and starts the existing agent run when that
application function returns `START_RUN`.

`handleConversationTurn` is already the useful application/service boundary.
It deterministically classifies and extracts first, uses the bounded model
fallback only when deterministic classification has no category, routes the
result through domain availability rules, and persists accumulated
`UserIntent` plus a capped transcript in `conversation_sessions`. The model can
propose an interpretation; it cannot write state or execute an order.

The rest of the relevant system is also already separated:

- buyer demand is `UserIntent` / `RunBrief`, then the existing agent run,
  discovery evaluation, quote, task, commitment, and fulfilment services;
- businesses and routes are the system of record, with `quickStartBusiness`,
  Tally normalization/onboarding, self-service profile/pricing operations, and
  operator-controlled activation all writing those same tables;
- printing products, minimum orders, fulfilment facts, and canonical Lagos
  coverage already live on the route/capability model;
- `/v1/:businessSlug/capabilities` and quote endpoints serialize and operate on
  those routes for external agents. There is no separate MCP-owned capability
  store;
- buyer identity is an opaque Web session; business authority is a scoped
  manage token; agent-originated work uses an agent session plus an optional
  buyer claim. These remain the authorization mechanisms in M10.16.

The missing seam is between a channel-specific delivery and the existing
application functions. The Web route currently performs normalization,
orchestration, agent-run dispatch, idempotency decisions, and response shaping
in one handler.

## Desired architecture

M10.16 adds the following narrow flow:

```text
channel adapter
  -> normalized inbound message + actor reference
  -> conversation gateway
  -> existing application/domain services
  -> structured, channel-independent result
  -> channel adapter response/delivery
```

The gateway is a function/module, not a new `ConversationService` abstraction.
For buyer turns it calls the existing `handleConversationTurn` application
function and existing agent-run service. Business facts are converted into the
existing quick-start/onboarding input and, only after validation and explicit
consent, use the existing business creation service. The gateway never writes
a second business or capability representation.

An `ActorReference` formalizes the identity the adapter has already
authenticated or resolved: role, channel-external user id, and optional
business id. The existing `conversation_sessions` row remains the durable
conversation aggregate and records the actor/channel/external-conversation
association alongside its accumulated state and transcript. Web buyer actors
resolve deterministically from the existing session id. Future business
adapters must resolve a manage-token-authenticated business before presenting a
business actor to the gateway.

Inbound messages carry an external message id. Gateway processing reuses the
existing durable idempotency store, scoped by channel and external
conversation, so a provider retry replays the first structured result rather
than executing the action again.

Structured audit events use the existing append-only audit table and contain
identifiers, roles, action kinds, and changed-field names—never raw message
text, contact details, or model prompts.

## Migration seams

The following stay unchanged:

- classification, extraction, routing, accumulated buyer intent, and response
  wording;
- agent discovery, candidate evaluation, quoting, commitments, approval, and
  fulfilment rules;
- canonical printing product and Lagos location vocabularies;
- Tally ingestion and its replay protection;
- business/route tables, operator verification, manage-token authorization,
  capability serialization, and `/v1` agent endpoints;
- Web response shape, apart from accepting an optional client-generated
  `messageId` and exposing gateway metadata additively.

Adding WhatsApp in M10.17 should therefore require an authenticated adapter
that converts provider webhook data into `InboundMessage` and delivers the
gateway's outbound messages. It must not require edits to discovery, quotes,
commitments, business capabilities, or buyer qualification.

## Risks and controls

- **Duplicated channel logic:** adapters only normalize identity/message data
  and deliver output; application actions remain in the gateway and existing
  services.
- **LLM-owned state:** model output continues through deterministic schemas and
  application merging before persistence. The gateway cannot accept an
  arbitrary database patch from a model.
- **Conversation state leaking into domain truth:** conversation facts remain
  provisional until an existing domain service validates and applies an
  explicit action.
- **WhatsApp-specific business logic:** no provider SDK, webhook shape, phone
  formatting rule, or message template enters the gateway.
- **Inconsistent identities:** adapters resolve an actor first; the durable
  conversation records that actor/channel association and rejects a session
  key reused for a different identity.
- **Competing capability representations:** conversational onboarding targets
  the same `businesses` and `quote_routes` records consumed by discovery and
  the capability API. Tally remains supported.
- **Replay races:** the existing idempotency table provides durable replay for
  ordinary provider retries. A future high-volume adapter should add a claimed
  processing state or queue-level serialization if providers can deliver the
  same message concurrently; this is not needed to couple the domain to a
  channel today.

## Deliberate M10.16 limits

No WhatsApp or Telegram integration is added. No identity-account migration,
new category taxonomy, multi-vertical onboarding, supplier dashboard, MCP
server, or transaction-in-chat behavior is introduced. Business creation still
produces a draft route and retains operator review and existing safety rules.
