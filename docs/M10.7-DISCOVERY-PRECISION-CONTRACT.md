# M10.7 — Discovery precision contract audit

**Goal, in one sentence**: define exactly how Intra should move from "find
providers for this route" to "find providers most likely to satisfy this
specific buyer request," without touching the discovery mechanism yet.

**Status**: audit and design only. No code, schema, migration, or dependency
change was made. Nothing here is implemented.

**Builds on**: `docs/M10.3-MARKETPLACE-SUPPLY-MODEL.md` (supply-model audit,
G1–G8) and `docs/M10.6-SHARED-CATEGORY-MULTISERVICE.md` (unified category
vocabulary, parameterised printing route). Both are read as ground truth
below; this document does not re-litigate them, only extends them toward
precision matching.

**Headline finding**: the codebase already has real, working pieces of every
stage in the target model — candidate retrieval (`discoverProviders`),
constraint evaluation (`policy/candidates.ts`), and comparison
(`policy/offers.ts`) all exist and are deterministic and explainable. What is
missing is not a new architecture; it is (a) supplier-side structured data for
the constraints that matter most — location and turnaround — which Tally
already collects and today silently discards (M10.3 G4, still open), and (b)
an explicit UNKNOWN state carried through candidate retrieval, instead of
constraints that either aren't evaluated pre-quote at all or are evaluated
only implicitly. The one piece of genuinely new design this milestone
proposes is a formal `CandidateEvaluation` result type that carries per-
constraint MATCH/NO_MATCH/UNKNOWN through to the buyer and the trace.

---

## 1. Core model (target, not yet built)

```
BUYER INTENT → CANDIDATE RETRIEVAL → CONSTRAINT EVALUATION → QUALIFIED SHORTLIST → QUOTE REQUEST → COMPARISON
```

Mapped onto what exists today (full detail in §16):

| Stage                 | Exists today?                                  | Where                                                              |
| --------------------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| Buyer intent          | Yes, two parallel representations (§16.1)      | `intent/types.ts` (`UserIntent`), `agent/types.ts` (`BuyerIntent`) |
| Candidate retrieval   | Yes, but single-key                            | `discoverProviders` → `GET /api/routes/active`                     |
| Constraint evaluation | Yes, partial — availability/freshness/fee only | `agent/policy/candidates.ts` (`assess`, `planCandidates`)          |
| Qualified shortlist   | Yes                                            | `CandidatePlan.toQuery` / `.skipped`                               |
| Quote request         | Yes                                            | `requestQuote` tool → `requestQuoteViaCapabilityApi`               |
| Comparison            | Yes, rich                                      | `agent/policy/offers.ts` (`scoreOffer`, `selectOffer`)             |

These stages are **not collapsed in code** — that part of the target model is
already true. The gap is in what constraint evaluation can actually see: it
correctly reasons over availability, price freshness, payment, and fee budget,
because those are the only per-candidate facts the system currently has
_before_ a human answers. Everything a buyer actually differentiates suppliers
by — can you serve my area, can you hit my quantity, can you meet my deadline
— is either evaluated only after a quote comes back (deadline, via
`scoreOffer`'s `MISSES_DEADLINE`) or not evaluated anywhere (location,
quantity vs. minimum order), because the supply side has no structured value
for it yet.

## 2. UNKNOWN as a first-class state

The codebase already has one clean precedent for this, worth generalising
rather than reinventing: `agent/policy/candidates.ts`'s `assess()` treats
`candidate.availability === null` (the capability document could not be read)
as its own `CAPABILITIES_NOT_READ` disqualifier — explicitly distinguished
from `!candidate.availability.acceptingQuoteRequests` (a real `NO_MATCH`). It
does not silently treat "unread" as "unavailable," and it does not treat it as
"available" either. That is exactly the discipline this milestone generalises
to every constraint.

**Rule**: UNKNOWN must never silently resolve to MATCH or NO_MATCH. Every
constraint's evaluator returns one of the three explicitly, and the candidate
evaluation contract (§5) carries the UNKNOWN reason forward so it can be
shown, not just internally suppressed.

**Per-constraint UNKNOWN policy** (detailed per-row in §3; summarised here):

| Effect of UNKNOWN                                      | When to use it                                                                                                                                                                       |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Leave eligible, no confidence penalty**              | The constraint is soft, or the buyer never stated a value for it (nothing to conflict with).                                                                                         |
| **Leave eligible, downgrade confidence**               | The constraint is hard in principle, the buyer stated a value, but supply data to check it is absent.                                                                                |
| **Exclude**                                            | Never appropriate purely from UNKNOWN in this milestone's recommended defaults — see below.                                                                                          |
| **Trigger a clarification question**                   | The missing value is on the _buyer's_ side and is required to even attempt evaluation (existing `ASK` flow in `routing.ts`).                                                         |
| **Trigger supplier confirmation via `requestQuote()`** | The missing value is on the _supplier's_ side and the constraint is hard — the honest way to resolve it is to ask the specific supplier, not to guess or exclude them pre-emptively. |

The recommended default, consistent with `CLAUDE.md` §4.1's fabrication rule
and the existing `CAPABILITIES_NOT_READ` precedent: **an UNKNOWN hard
constraint downgrades confidence and/or defers resolution to
`requestQuote()`; it does not exclude the candidate.** Excluding on UNKNOWN
would systematically punish suppliers for Intra's own missing data (most
suppliers today, since service area is never persisted — see §8), which is a
worse failure mode than asking. The one exception the current code already
enforces correctly and should keep: a **read failure** on a required
capability document (`CAPABILITIES_NOT_READ`) does exclude, because an agent
must not spend a fee or a human's time against a candidate it could not even
check for the hard gate (availability) that already has to be true for
anyone.

## 4. Hard vs. soft constraints

**Hard** (a violation is a `NO_MATCH`, and a confirmed `NO_MATCH` excludes):
category/service (#1–2), a confirmed service-area mismatch (#6, only when
known), a confirmed minimum-order violation (#10, only when known), a
confirmed inability to meet a stated deadline (#8/#9, only when known — today
this is confirmed post-quote via `scoreOffer`, never pre-quote), route
availability (#13), and supplier verification (#15).

**Soft** (a ranking signal, never an exclusion on its own): pricing model and
published price (#11–12, except the narrow stated-budget-versus-comparable-
price case noted in the table), fulfilment preference when only "preferred,"
distance/city as a tiebreaker, and — the existing, working example —
`scoreOffer`'s price/turnaround/confidence/validity scoring, which already
treats these exactly as ranking signals rather than eligibility gates.

**The critical distinction this audit surfaces**: for six of the fifteen
constraints (#3, #4 supplier-side, #5/#6, #7, #9/#10), Intra does not
currently have enough supplier data to know whether they are even a genuine
hard-fail or a false one. A constraint being _conceptually_ hard (a real
minimum-order violation should exclude a candidate) does not make it safe to
enforce today, because "no minimum order was declared" and "the minimum
order genuinely does not exceed the buyer's quantity" are indistinguishable
in the current data model — both read as `null`. Treating that `null` as a
hard `NO_MATCH` would be a fabrication in the other direction (inventing a
supplier limitation that was never stated). This is why §2's UNKNOWN policy
insists on "downgrade or ask," never "exclude," for a hard constraint with no
supplier data behind it yet.

## 5. Candidate evaluation contract

The milestone brief's own sketch is a good fit; the recommendation below
keeps its shape and grounds every field in a type or concept that already
exists in the codebase, so this is a genuine extension rather than a parallel
system.

```ts
interface ConstraintResult {
  status: "MATCH" | "NO_MATCH" | "UNKNOWN";
  /** Present for NO_MATCH and UNKNOWN; a human-readable reason, in the same
   *  voice as the existing `DecisionReason.statement` (agent/types.ts). */
  detail?: string;
}

interface CandidateEvaluation {
  candidate: ProviderCandidate; // reuse agent/types.ts, unchanged
  constraints: {
    category: ConstraintResult; // always MATCH — filtered upstream by routeSlug
    service: ConstraintResult; // always MATCH — same reason
    productType: ConstraintResult; // UNKNOWN today, always
    quantity: ConstraintResult; // UNKNOWN today (no minimum order data)
    location: ConstraintResult; // UNKNOWN today (no service area data)
    fulfilment: ConstraintResult; // UNKNOWN today
    deadline: ConstraintResult; // UNKNOWN pre-quote; resolved post-quote by scoreOffer
    availability: ConstraintResult; // real MATCH/NO_MATCH/UNKNOWN today, via routeIsQuoteReady
    verification: ConstraintResult; // real MATCH/NO_MATCH today
    pricing: ConstraintResult; // soft; UNKNOWN unless FIXED + published + stated budget
  };
  overall: {
    status: "ELIGIBLE" | "EXCLUDED" | "NEEDS_CONFIRMATION";
    confidence: "HIGH" | "MEDIUM" | "LOW";
  };
}
```

Deriving `overall` from `constraints`, as a pure function (mirrors
`agent/policy/candidates.ts`'s existing style — a `disqualifiers.length === 0`
check plus a priority score):

- **EXCLUDED**: any hard constraint is `NO_MATCH`, OR the capability document
  itself could not be read (the existing `CAPABILITIES_NOT_READ` case).
- **NEEDS_CONFIRMATION**: no hard constraint is `NO_MATCH`, but at least one
  hard constraint the buyer actually stated a value for is `UNKNOWN`.
- **ELIGIBLE**: every hard constraint is `MATCH`, or `UNKNOWN` only where the
  buyer never stated a value to conflict with in the first place.
- **confidence**: `HIGH` when every stated hard constraint is `MATCH`;
  `MEDIUM` when one or more is `UNKNOWN` (i.e. `NEEDS_CONFIRMATION`); `LOW`
  when a soft constraint is unfavourable (e.g. price above a stated budget on
  a non-`FIXED` model) even though the candidate is still `ELIGIBLE`.

This is additive over the existing `CandidateAssessment`
(`agent/policy/candidates.ts`) — it does not replace `queryable`,
`disqualifiers`, `reasons`, or `priority`, all of which remain valid and keep
their current meaning. `CandidateEvaluation.overall.status === "EXCLUDED"`
would replace `queryable === false`; `NEEDS_CONFIRMATION` is new information
`CandidateAssessment` cannot currently represent (today, an unresolvable
constraint is just silently absent from evaluation rather than surfaced as a
distinct state).

## 6. Discovery depths

| Depth                     | Known                                                             | Purpose                                                            | Maps to existing code                                                                                                                                                                                                                                                                |
| ------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1 — broad**             | service/category                                                  | Find possible suppliers; identify what's still missing             | `discoverProviders` alone, before `missingForQuote`/`missingBriefFields` gates are satisfied — this already happens implicitly the moment `resolveDomain` succeeds, but nothing surfaces a Depth-1 result to the buyer today; the conversation layer skips straight past it (see §7) |
| **2 — qualified**         | service, quantity, location, deadline/fulfilment where applicable | Remove suppliers that clearly cannot satisfy material requirements | **Does not exist today.** `agent/policy/candidates.ts`'s `assess()` is the closest thing, but it only evaluates availability/freshness/fee — none of quantity, location, or deadline, because the supply data for them doesn't exist (§3)                                            |
| **3 — transaction-ready** | enough detail to request quotes                                   | Produce a small qualified set for `requestQuote()`                 | `missingBriefFields` (flyer-printing-specific) / `missingForQuote` (domain-general) gate this correctly today — a request is never sent to `requestQuote()` with a field the receiving route's own schema would 422 on                                                               |

**Today's actual behaviour is Depth 1 candidate retrieval immediately
followed by a jump to Depth 3's completeness gate, with no real Depth 2 in
between.** `routing.ts`'s `DISCOVERY` / `COMPARISON` / `QUOTE_REQUEST` cases
all resolve to the exact same branch: check `missingForQuote`, and either ask
for what's missing or go straight to `START_QUOTE`. There is no intermediate
state where the buyer sees "3 possible printers, here's what's still
missing" — discovery is invisible until quote-request-readiness is reached,
at which point `discoverProviders` runs once and its candidates are the first
thing the buyer implicitly learns about (via the final recommendation, not a
narrated shortlist).

This is not necessarily wrong for a single-route MVP (there is exactly one
live route today, so a Depth 2 filter has nothing to filter with real data
yet — see §3's location/quantity rows). It becomes necessary the moment (a) a
second business exists on the one live route with genuinely different
location/service-area data, or (b) a second category goes live. Per the
milestone's own instruction ("do not force every conversation through
maximum depth"), the recommended design is that Depth 2 filtering activates
_only_ for the constraints that have real data — i.e., it should be written
to silently no-op today (because service area doesn't exist yet) and start
filtering the moment §8's data exists, without a second implementation pass.

## 7. Conversation ↔ discovery loop

**Today's actual loop**, traced through `routing.ts` and
`agent/runtime/loop.ts`:

1. `handleConversationTurn` classifies the message into a `ConversationIntent`
   and merges extracted fields into the session's persisted `UserIntent`
   (`intent/repository.ts`, M10.4).
2. `routeReading` resolves the domain, then calls `missingForQuote(domain,
intent)`. If anything is missing, it returns `{ kind: "ASK", missing }`
   with a **generic** describe-missing message (`reply.ts`'s
   `describeMissing`) — this never runs discovery to check whether the
   missing field would actually change eligibility, because there is nothing
   for it to check against (§3, §6).
3. Only once every `requiredForQuote` field is present does `routing.ts`
   return `START_QUOTE`, which becomes `startAgentRun`
   (`app/api/conversation/route.ts`).
4. Inside the agent run, a **second**, independent completeness gate re-runs
   — `missingBriefFields` (flyer-printing's own 5-field list) — because the
   agent loop re-parses the raw text into `BuyerIntent` rather than trusting
   the conversation layer's `UserIntent` wholesale (only `briefCorrection`,
   the mapped subset, crosses over — see §16.1 for why these are two
   different types).
5. Discovery (`discoverProviders`) runs only after step 4 passes, once, and
   its result is never fed back into the conversation layer to ask a
   _further_ narrowing question — `agent/policy/candidates.ts`'s
   `assess()` runs immediately after, deterministically, with no
   human-in-the-loop turn in between.

**What the milestone brief's example ("I need 500 flyers" → ask for
deadline only if it materially changes eligibility") would require that
doesn't exist today**: a way to know, for a _specific_ missing field, whether
resolving it would actually change which candidates are eligible. Currently
`missingForQuote`/`missingBriefFields` ask for a field because the **route's
input schema requires it to accept the request at all** (a validation
concern), not because discovery has determined it's material to _which
supplier_ would be shown (an eligibility concern). These happen to coincide
today only because Depth 2 doesn't exist yet (§6) — once it does, the two
questions ("is this field required by the route schema" vs "would knowing
this field change who's eligible") become genuinely different, and the loop
needs to ask the second, not just the first.

**Recommended shape** (design only, not built): after Depth 1 candidate
retrieval, compute `CandidateEvaluation` (§5) for every candidate against
what's known so far. If every remaining candidate's status is `ELIGIBLE`
regardless of a still-missing field, do not ask for it before quoting — let
`requestQuote()` carry the gap to the specific supplier (per §2's UNKNOWN
policy). Only ask when a missing field would flip at least one candidate
between `ELIGIBLE` and `EXCLUDED`/`NEEDS_CONFIRMATION`. This subsumes, rather
than replaces, today's route-schema-required-field gate: a field can still be
required by the route schema (so the request would 422 without it) even when
it wouldn't change eligibility — in that case, ask for it, but frame the
question as "the printer needs to know X to quote you" rather than "I need X
to find who can help," since those are honestly different reasons and the
buyer should be told which one applies. **Do not repeatedly ask for
information already known** — this is already respected by construction
today, since `missingForQuote`/`missingBriefFields` only ever check fields
that are still absent from the accumulated `UserIntent`/re-parsed text.

## 8. Supplier data requirements

For each material constraint, what the supplier must declare, and the
concrete evaluation outcomes:

| Constraint              | Supplier must declare                                                  | MATCH                                                 | NO_MATCH                                  | UNKNOWN                                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |

| Fulfilment              | Pickup available? Delivery available?                                  | Buyer's preference matches a `true` flag              | Buyer's preference matches a `false` flag | Neither flag was recorded (**today's actual state** — collected by Tally, never persisted)                                    |

row above that isn't even collected yet, and would need a new Tally question
(out of scope to add here — this is an audit, not a form change) before it
could be promoted at all.

## 9. Location model recommendation

Do not build geospatial/radius discovery (per the milestone's explicit
instruction). Comparing the options against what the domain already speaks
in:

- **City** — already a structured column on `businesses` (`city`, `country`).
  Coarse; two businesses in the same Lagos suburb but opposite ends of the
  city both read as a city match. Cheapest to use, already there, but not
  precise enough on its own for "near Yaba."
- **Area/neighbourhood** (e.g. "Yaba", "Surulere") — this is what buyers
  actually say (`UserIntent.location`, `deliveryArea` in the flyer-printing
  brief) and what Tally already collects as free text (`serviceArea`). No
  normalisation or gazetteer exists — "Yaba" vs. "yaba " vs. "UNILAG main
  gate" are three different strings today.
- **Service area (a supplier's declared coverage, possibly a list of
  areas)** — the correct target representation: it directly answers "does
  this supplier serve where the buyer is," which is what the buyer's
  question actually is, without pretending to precise geography.
- **Pickup location vs. delivery coverage** — genuinely two different
  concepts already reflected in Tally's two separate booleans
  (`pickupAvailable`/`deliveryAvailable`) plus the free-text `serviceArea` —
  a pickup-only business's "coverage" is really just its single address, a
  delivery business's is a set of areas.
- **Delivery-only restrictions** — not asked anywhere today (Tally has no
  "we only deliver, no walk-ins" question distinct from the two booleans
  above, though the two booleans together already imply it: `pickupAvailable
= false, deliveryAvailable = true`).

**Recommendation**: represent supplier location as **free-text service area
(one string or a short list of area names) plus the two existing pickup/
delivery booleans**, matched against the buyer's free-text location via
simple case-insensitive substring/contains matching initially — not
geocoding, not a radius, not even a controlled vocabulary yet. This is
deliberately the least precise representation that is still honest: a
substring match on "Yaba" will MATCH "Yaba and Akoka" and correctly return
UNKNOWN (not NO_MATCH) for a differently-worded area, because a
false-negative NO_MATCH on a location constraint (silently hiding a supplier
who might actually serve the area) is a worse failure than an over-broad
MATCH set the buyer then narrows via quote responses. A controlled
neighbourhood vocabulary is a legitimate future step but is exactly the kind
of "pretending to have precise geographic coverage" the milestone brief
warns against building prematurely.

## 10. Quantity / minimum order model

```
buyer = 500, minimum = 100   → MATCH
buyer = 50,  minimum = 100   → NO_MATCH
minimum unknown              → UNKNOWN
```

This is exactly the milestone brief's own example, and nothing in the current
codebase contradicts it — there is simply no `minimum order` field to
evaluate against yet (§3 row 10, §8). **Do not infer capacity beyond explicit
data**: no heuristic (e.g. "printers who publish `STARTING_FROM` pricing
probably have a floor") should stand in for an actual declared minimum,
because that would be exactly the kind of fabricated supply-side capability
`CLAUDE.md` §4.1 prohibits in spirit, even though it targets payments/
attestations specifically. The buyer's quantity itself is already reliably
structured (`UserIntent.quantity`, validated as a positive integer by
`flyerPrintingInputSchema`) — the constraint is fully ready on the buyer side
and entirely unimplementable on the supply side until a minimum-order
question is added to onboarding, which is out of scope for this audit.

## 11. Deadline / turnaround model

Three tiers, matching the milestone brief's own distinction, mapped onto what
the codebase can actually say today:

1. **Explicit guaranteed capability** — a supplier states a turnaround
   _specifically for this job_ — this is exactly what `quotes.turnaround`
   already is (a field on a returned `QuoteRow`, filled in by the human
   supplier when they answer). `scoreOffer`'s `MISSES_DEADLINE`/
   `MEETS_DEADLINE` already evaluates this correctly, post-quote, against
   `intent.deadline`. This tier is well-built today.
2. **Stated typical turnaround** — a route-level "we usually take about 2
   days" figure that could be checked _before_ a quote is requested, to avoid
   wasting a quote-request round-trip on a structurally infeasible ask. This
   tier **does not exist** — it is exactly the free-text `turnaround` Tally
   collects and discards (§3 row 9, §8).
3. **Unknown turnaround** — today's actual state for every route,
   pre-quote, because tier 2 doesn't exist. Handled correctly by the _design_
   of the current flow: rather than guessing, the system defers to tier 1
   (ask the specific supplier via `requestQuote()`) and evaluates feasibility
   only once a real answer exists. This is the one constraint in the entire
   catalogue where "resolve via asking" is not a future recommendation — it
   is what the code already does, and it is the right behaviour to keep.

**A distinction worth stating explicitly for the implementing milestone**:
`route.responseSlaMinutes` (how fast a supplier commits to _responding_ to a
quote request) must never be read as, or presented as, turnaround (how fast
they'd _complete the job_). Nothing in the current codebase conflates them —
`capability.ts`'s `quoteSla` and a hypothetical future `turnaround` field are
cleanly separable concepts — but the two are similar enough in shape (both
"how fast," both minutes/days) that a future implementer promoting tier 2
into a real column should not accidentally source it from
`responseSlaMinutes`.

## 12. Availability model

**CAPABLE vs. CURRENTLY ACCEPTING REQUESTS** is already a real, working
distinction in the codebase — this is the constraint the system models best.
`routeIsQuoteReady` (`routes/freshness.ts`) computes exactly this separation:

- A route can be **capable** (it exists, has a template, in principle could
  serve flyer printing) while being **not currently accepting requests**
  because it is `DRAFT`/`PAUSED`/`ARCHIVED` (`NOT_ACTIVE`), unverified
  (`NOT_VERIFIED`), or its price data has aged out (`STALE`).
- The four-way `RouteReadyReason` (`OK` / `NOT_ACTIVE` / `NOT_VERIFIED` /
  `STALE`) is exactly a MATCH/NO_MATCH breakdown with named reasons, already
  exposed verbatim to agents via `ROUTE_READY_DETAIL` in the capability
  document.
- **Preserve the existing ACTIVE route requirement** (explicit milestone
  instruction): nothing here proposes loosening `routeIsQuoteReady`'s
  `status !== "ACTIVE"` check — a paused route must keep failing this
  constraint exactly as it does today.

**Gap** (already flagged in §3 row 14, repeated here because it belongs to
this section conceptually): `businesses.status` — a genuinely separate
"currently accepting requests" signal at the _business_ level (a business
account itself could be `PAUSED` while an individual route row is left
`ACTIVE`) — is **not** part of `routeIsQuoteReady`'s computation. Today the
only business-level check is `verifiedByOperatorAt !== null`, which answers
"was this business ever verified," not "is it currently operating." This is
a pre-existing gap this audit surfaces rather than a regression risk from
anything proposed here.

## 13. Quote eligibility

**Which candidates reach `requestQuote()`**: today, exactly the candidates
`agent/policy/candidates.ts`'s `planCandidates` places in `toQuery` — i.e.
`queryable === true` (no disqualifier fired), sorted by priority, capped at
`maxProviders` (default 3), and further capped by the run's fee budget. This
already implements the milestone's own recommendation ("do not request
quotes from clearly excluded suppliers") for the constraints it currently
evaluates (availability, freshness, fee).

**Recommended rule once `CandidateEvaluation` (§5) exists**: a candidate
reaches `requestQuote()` when `overall.status` is `ELIGIBLE` **or**
`NEEDS_CONFIRMATION` — never when `EXCLUDED`. This matches §2's UNKNOWN
policy directly: `NEEDS_CONFIRMATION` exists specifically to be resolved by
asking the supplier via the quote request itself, not by holding the
candidate back pending more buyer-side data Intra may never get. Concretely,
under this rule, every one of today's UNKNOWN-because-unpersisted
constraints (location, fulfilment, quantity-vs-minimum, subtype) would leave
a candidate `NEEDS_CONFIRMATION`, not `EXCLUDED` — behaviourally identical to
today (since nothing currently filters on them at all), but now the buyer/
trace can honestly say _why_ a candidate is only tentatively a good fit
rather than presenting it with unearned certainty.

## 14. Ranking inputs

No ML, no reputation score, no learned weights — matches the existing
`scoreOffer` design exactly (`agent/policy/offers.ts`), which is already a
hand-written, fully-explained point system: price (`10_000 / totalMin`),
turnaround (`120 - hours`, floored at 0), a flat `FIXED`-price bonus (+40), a
confidence bonus (`high: 30, medium: 15, low: 0`), and a remaining-validity
bonus (up to +60, capped). Every point added has a `DecisionReason` sentence
attached — this is already the "explainability by construction" the
milestone brief asks for (§15), not a future goal.

**Minimum ranking inputs, confirmed against what's real today**: price (real,
post-quote), turnaround (real, post-quote), fit (today only availability/
freshness/fee pre-quote — location/quantity/subtype fit does not exist to
rank on yet), confidence (real — the supplier's own stated confidence on a
quote), explicit buyer preferences (`UserIntent.optimization`: `CHEAPEST` /
`NEAREST` / `FASTEST` / `BEST_VALUE` / `AVAILABLE_NOW` / `WITHIN_BUDGET` /
`EARLIEST` — captured on the buyer side but **not currently read by
`scoreOffer`**, which always applies the same fixed weighting regardless of
what the buyer said they cared about — see §17 gap G-10.7-3). No reputation/
history-based scoring exists or is proposed; `handedOff`/Proofline
attestation history (`routes/reads.ts`'s `SupplierWorkspace.handedOff`)
exists for operator visibility but is never read into ranking, consistent
with the milestone's explicit instruction not to introduce it yet.

## 15. Explainability

Already strong, in both directions, for the constraints that exist:

- **Positive** ("why did you show me this supplier?"): `scoreOffer`'s
  `reasons` array is literally sentences like "Offers flyer printing and
  meets your quantity" in spirit — concretely today, `"${business} can
deliver in ${turnaround}, inside the ${hours}h available"`,
  `"${business} is verified and taking requests"`. `buildRecommendationDetail`
  (`quotes/recommendation.ts`) does the same for the final single-quote
  explanation shown to the buyer.
- **Negative** ("why was this excluded?"): `disqualifiers` on both
  `CandidateAssessment` and `ScoredOffer` are exactly this — e.g.
  `"Minimum order is 1,000; you requested 500"` is not a real message today
  only because minimum order isn't a real constraint yet (§10); the
  _pattern_ (`MISSES_DEADLINE`: `"${business}'s stated turnaround of
${turnaround} does not fit the ${hours}h left before the deadline"`) is
  already exactly this shape.
- **Never generated from guessed data** (explicit milestone requirement):
  already true by construction — every `DecisionReason.statement` in the
  current code is built from a real field on `ProviderCandidate`/
  `ProviderOffer`/`QuoteRow`, never a placeholder or invented value. This
  discipline should extend unchanged to any new `ConstraintResult.detail`
  string (§5): a `NO_MATCH`/`UNKNOWN` detail must quote or paraphrase an
  actual stored value or its explicit absence, never invent one.

**What §5's `CandidateEvaluation` adds that doesn't exist today**: the
_positive_ case for an `UNKNOWN` constraint specifically — e.g. "possible
match, but delivery coverage was not specified" (the milestone's own
example). Today, a constraint the system cannot evaluate simply doesn't
appear in `reasons` or `disqualifiers` at all; it is invisible rather than
explicitly named as unknown. This is the main behavioural gap explainability-
wise, not a missing capability — the sentence-generation pattern to fill it
with already exists and just needs a third branch (`UNKNOWN` alongside
`MATCH`/`NO_MATCH`) added to it.

## 16. Current code mapping

### 16.1 Two parallel buyer-intent representations

A structural fact load-bearing enough to call out on its own: the codebase
carries **two independent "what does the buyer want" types**, not one.

- **`UserIntent`** (`intent/types.ts`) — domain-neutral, accumulated across
  turns, persisted per session (`intent/repository.ts`, M10.4). Fields:
  `goal`, `category`, `service`, `quantity`, `size`, `colour`, `budget`,
  `location`, `deadline`, `availabilityRequired`, `condition`,
  `optimization`, `fulfillmentPreference`. This is what the conversation
  layer (`conversation.ts`, `routing.ts`, `extract.ts`) reads and writes, and
  it is genuinely category-general — it has fields no printing request would
  ever use (`condition`, `availabilityRequired`) precisely because it's meant
  to serve every future `DomainCapability`.
- **`BuyerIntent`** (`agent/types.ts`) — flyer-printing-specific, re-parsed
  from raw text on every run by `agent/runtime/intent.ts`'s deterministic
  parser (`parseQuantity`, `parseDeadline`, `parseSize`, `parseColour`).
  Fields: `raw`, `quantity`, `deadline`, `size`, `colour`, `deliveryArea`,
  `maxQueryFeeUsd`. This is what `discoverProviders`,
  `agent/policy/candidates.ts`, and `agent/policy/offers.ts` actually
  consume.

The bridge is `conversation.ts`'s `toRunBrief()`, which maps a **subset** of
`UserIntent` onto the agent's `RunBrief`/`briefCorrection` shape (`quantity`,
`size`, `colour`, `deadline.iso`, `location` → `deliveryArea`) — notably
**not** `fulfillmentPreference`, `budget`, `optimization`, or `condition`,
which the conversation layer already captures but which never reach the
agent loop in any form. This is consistent with the finding in §3/§7/§14:
several `UserIntent` fields exist and are populated, but have no consumer
downstream once the agent run actually starts, because the agent run today
only understands the fixed flyer-printing brief shape.

This split exists for a defensible reason (`BuyerIntent`'s deterministic
parser must produce the same brief with or without a model key — CLAUDE.md
§6.2's ADR-019 constraint), and this audit does not recommend collapsing it.
It is flagged here because §6's "Depth 2 filtering" and §14's "read buyer
preference into ranking" both require deciding, deliberately, which of these
two types the new logic reads from — today that choice is implicit and
inconsistent (routing reads `UserIntent`; policy reads `BuyerIntent`).

### 16.2 `discoverProviders()`

`agent/tools/registry.ts` → `GET /api/routes/active?routeSlug=`
(`app/api/routes/active/route.ts`) → one query:
`WHERE quote_routes.slug = :routeSlug AND quote_routes.status = 'ACTIVE'`,
joined to `businesses` for display fields only (`city`, `country`,
`businessName`). No filter on verification, freshness, business status,
location, quantity, or price. This is deliberate and correct for candidate
_retrieval_ per the target model (§1) — broad on purpose — but it means
`discoverProviders` today returns candidates that `agent/policy/candidates.ts`
will immediately disqualify (e.g. a stale or unverified `ACTIVE` route), which
is fine architecturally (constraint evaluation is a separate stage) but is
worth naming precisely: **the "candidates" a buyer-facing trace calls
"found" at the `PROVIDERS_FOUND` reasoning step (`loop.ts` line 367) have not
yet been checked for availability at all** — that only happens in the very
next stage.

### 16.3 `/api/routes/active`

Covered above; also the mechanism `agent/tools/registry.ts`'s
`discoverProviders` tool wraps. Confirmed unchanged since the M10.3 audit.

### 16.4 Capability generation

`buildBusinessCapabilities()` (`routes/capability.ts`) is unchanged in shape
since M10.3/M10.6 except for the `options` passthrough added in M10.6. It
remains the single derived source (no separate store), returns **every**
route on a business with an explicit per-route `availability` object rather
than filtering silently, and is the only place `routeIsQuoteReady` is
actually invoked to produce a candidate-facing verdict.

### 16.5 Route templates

`routes/templates.ts`'s `SERVICE_TEMPLATES`, `getTemplatesForCategory`,
`defaultTemplateFor` — unchanged since M10.6. Category-to-template mapping
remains code-owned and versioned with the app, per M10.3 §9 principle 2 (no
services table) — this audit finds no reason to revisit that.

### 16.6 Onboarding data

`onboarding/normalize.ts` reads `serviceArea`, `pickupAvailable`,
`deliveryAvailable`, `turnaround`, `responseTime` from every Tally
submission. `onboarding/service.ts`'s `createBusinessFromOnboarding` persists
only `slug`, `name`, `contactName`, `contactChannelType`,
`contactChannelValue`, `category`, `city`, `country`, `payoutAddress`,
`quoteCurrency`, `consentAt`, `status` — confirming M10.3's G4 is **still
fully open**: all four of `serviceArea`/`pickupAvailable`/
`deliveryAvailable`/`turnaround` survive only in
`onboarding_submissions.normalizedData` (an untyped `jsonb` column, per
`lib/db/schema.ts` line 624) and are never promoted. `responseTime` is the
one exception — it **is** promoted, via `route.responseSlaMinutes`
(`QUOTE_RESPONSE_TIME_MINUTES` mapping in `businesses/schema.ts`), which is
exactly why it participates in ranking today (`agent/policy/candidates.ts`'s
`slaScore`) while the other three don't participate in anything.

### 16.7 Quote creation

`requestQuoteViaCapabilityApi` (`routes/quote-request.ts`) validates against
`flyerPrintingInputSchema` for the one live route (or `validateGeneric`
against `route.inputSchema` for any other), re-checks `routeIsQuoteReady`
independently of whatever the agent's own pre-check found (defense in depth —
a route could theoretically go stale between discovery and the actual quote
POST), and creates a `tasks` row via the existing `DRAFT → SUBMITTED →
AWAITING_QUOTE` lifecycle. No changes here relative to M10.3/M10.6; this
stage is unaffected by anything this milestone proposes.

### 16.8 Comparison

`agent/policy/offers.ts`'s `scoreOffer`/`selectOffer` — covered fully in
§11/§14. This is the most mature stage in the entire pipeline and needs no
structural change; it only needs feeding.

### 16.9 Conversation intent state

`intent/domain.ts` (M10.6-unified vocabulary), `intent/routing.ts`,
`intent/conversation.ts`, `intent/repository.ts` (M10.4 persistence) —
covered in §7 and §16.1. No inaccuracy found relative to the M10.6 report;
behaviour is exactly as that document describes.

## 17. Exact gaps

**G-10.7-1 — `productType` is built but unused for matching.** M10.6 added a
real, per-business `productType` options list to the printing route's
`inputSchema`, populated from actual Tally submissions
(`enrichPrintingRoute`). Nothing reads it: not `UserIntent` (no field for a
buyer-stated product type), not `BuyerIntent` (same), not
`agent/policy/candidates.ts` (no subtype constraint), not `discoverProviders`
(routeSlug-only). A buyer who says "I need banners" today is not directed
toward, or away from, any specific printer based on that word — the model-
assisted brief interpretation (`assist.ts`) may capture "banners" as free
text within `service`, but it is never checked against any supplier's
declared `productType.options`.

**G-10.7-2 — `businesses.status` does not gate discovery or availability.**
Detailed in §3 row 14 and §12. A `PAUSED` business with a route still marked
`ACTIVE` would currently still surface via `discoverProviders` and still
report `availability.state: "AVAILABLE"` from `buildBusinessCapabilities`, as
long as `verifiedByOperatorAt` and route-level freshness/status are
satisfied. Whether this is a real operational risk depends on whether the
existing route-lifecycle code (`routes/service.ts`) ever leaves a route
`ACTIVE` while its business is `PAUSED` in practice — that lifecycle
question is outside this audit's scope, but the discovery-layer gap itself is
real and independent of how often it's hit today.

**G-10.7-3 — `UserIntent.optimization` is captured but not read by
ranking.** The buyer's explicit stated preference (`CHEAPEST`, `NEAREST`,
`FASTEST`, `BEST_VALUE`, `AVAILABLE_NOW`, `WITHIN_BUDGET`, `EARLIEST`) is
extracted by `extract.ts` and stored on `UserIntent`, but `toRunBrief()`
never forwards it, and `scoreOffer` always applies the same fixed weighting
(price-heavy, per §14) regardless. A buyer who explicitly says "I don't care
about price, I need it fastest" is scored identically to one who said
nothing about preference at all.

**G-10.7-4 (restates M10.3 G4, confirmed still open) — service area,
fulfilment method, and turnaround are collected but discarded.** The single
largest blocker to any real Depth 2 filtering (§6) or location/fulfilment/
deadline constraint evaluation (§3 rows 6, 7, 9). Every downstream design in
this document that depends on real supplier-side location or turnaround data
(§5's `NEEDS_CONFIRMATION` path, §6's Depth 2, §9's recommended location
model, §11's tier-2 turnaround) is currently exercising a no-op path for
exactly this reason. This is not new — M10.3 named it — but M10.7 confirms
it is the load-bearing gap for precision discovery specifically, more than
any other single item on this list.

**G-10.7-5 — no minimum-order field exists anywhere, including in Tally.**
Distinct from G-10.7-4: this isn't discarded data, it was never asked for.
Closing it requires an onboarding-form change (a new Tally question), which
is out of scope for both this audit and, per the milestone brief's own
"do NOT build" list, likely out of scope for the immediate implementing
milestone too — noted here so it isn't mistaken for a data-promotion task
like G-10.7-4.

**G-10.7-6 — no formal UNKNOWN-carrying evaluation type exists yet.** §5's
`CandidateEvaluation`/`ConstraintResult` do not exist in any form today.
`CandidateAssessment` (`agent/policy/candidates.ts`) is a real, working
partial implementation of the same idea, but it conflates "not evaluated"
with "not disqualified" — a constraint with no evaluator (location, quantity,
subtype) simply never appears in `reasons` or `disqualifiers`, rather than
appearing as an explicit `UNKNOWN`. This is the specific, scoped gap this
milestone's own design work (§5) is meant to close.

## 18. Recommended implementation order

Ordered by leverage and dependency, mirroring the sequencing discipline
M10.3/M10.6 already established (cheapest, most-unlocking change first):

1. **Promote service area, pickup/delivery, and turnaround from Tally into
   real columns** (closes G-10.7-4 — the load-bearing blocker for nearly
   everything else on this list; M10.3 §10 item 4 already recommended
   `serviceArea` first, for exactly this reason). This is the one item on
   this list that needs a migration, and it should be scoped minimally: add
   the columns, promote the existing (already-collected, already-normalized)
   data through `createBusinessFromOnboarding`/`enrichPrintingRoute`-style
   enrichment — no new Tally questions, no UI change, no discovery change
   yet.
2. **Introduce `CandidateEvaluation`/`ConstraintResult` as an additive layer
   over `CandidateAssessment`** (closes G-10.7-6), wired only to the
   constraints that already have real data at that point: availability,
   verification, freshness/fee (already real), plus location and fulfilment
   now that step 1 exists. Quantity-vs-minimum-order and product-subtype
   stay `UNKNOWN` until their own data exists (steps 3/4).
3. **Wire `productType` into matching** (closes G-10.7-1) — extend
   `UserIntent`/`BuyerIntent` to optionally capture a stated product subtype,
   and evaluate it against each candidate's `inputSchema.options` as a new
   constraint in step 2's evaluator. Low cost: the supply-side data already
   exists from M10.6; only the demand-side capture and the comparison are
   new.
4. **Feed `UserIntent.optimization` into `scoreOffer`'s weighting** (closes
   G-10.7-3) — a scoped, self-contained change to `agent/policy/offers.ts`'s
   scoring weights, gated on the buyer's stated preference, with no schema
   or discovery impact.
5. **Minimum order** (closes G-10.7-5) — deferred last because it requires a
   product decision (a new onboarding question) outside engineering's
   remit, not because it's technically hard once asked for.
6. **`businesses.status` in the availability check** (closes G-10.7-2) —
   deferred not because it's low-value, but because it's an independent
   correctness fix to `routeIsQuoteReady` with its own blast radius
   (anything currently relying on today's behaviour, including the six-item
   activation checklist's assumptions) and deserves its own review rather
   than riding in on a discovery-precision milestone.

Each step above is independently shippable and independently testable, and
none requires reopening a decision this document or M10.3/M10.6 already made
— consistent with the instruction to produce a canonical blueprint, not a
sequence of speculative rewrites.
