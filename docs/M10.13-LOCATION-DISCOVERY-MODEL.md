# M10.13 — Location-aware discovery model audit

**Status:** audit only. No code, migration, Tally form, capability contract, or
quote-eligibility change is proposed in this milestone.

## Decision

For the Lagos pilot, retain location as **advisory**. Keep the current
conservative text-overlap MATCH rule and never derive a location NO_MATCH from
free text. Fulfilment remains independently authoritative: a declared
delivery/pickup `false` for the buyer's explicit method is a reliable
NO_MATCH, irrespective of location text.

The smallest next model worth implementing is not geocoding: a canonical,
city-scoped controlled area identifier list, with supplier delivery coverage
and pickup point recorded separately. It may become authoritative only after
the evidence requirements below are met.

## 1. Current data flow and limitations

| Stage                 | Current field                                       | Transformation                                                       | Limitation                                                  |
| --------------------- | --------------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------- |
| Buyer message         | text                                                | `extract.ts` reads a free-text `UserIntent.location`                 | “Yaba”, “around Yaba”, and landmarks are not canonicalized  |
| Conversation hand-off | `RunBrief.deliveryArea`                             | copied from `UserIntent.location`                                    | wording is preserved, not normalized                        |
| Agent brief           | `BuyerIntent.deliveryArea`                          | applied as a correction, then passed to `DiscoveryCriteria.location` | field name implies delivery even for pickup                 |
| Supplier onboarding   | Tally `service_area`                                | normalized as trimmed free text                                      | combines delivery coverage and pickup wording in one answer |
| Route                 | `quote_routes.serviceArea`                          | direct Tally passthrough                                             | no city/area/landmark structure                             |
| Capability/candidate  | `RouteCapability` → `ProviderCandidate.serviceArea` | copied unchanged                                                     | absence correctly remains null                              |
| Evaluation            | `evaluateLocation`                                  | comma-separated conservative substring overlap                       | can MATCH; intentionally cannot prove NO_MATCH              |

No stage geocodes, guesses a boundary, or derives service coverage from a
business city. This is correct. `businesses.city` is business location for
display; it is not delivery coverage, pickup point, or evidence of a match.

## 2. Location concepts

| Concept           | Exists now?    | Current source                                | Safe use today                 |
| ----------------- | -------------- | --------------------------------------------- | ------------------------------ |
| Business location | Partial        | business city/country                         | Display only                   |
| Pickup location   | No             | pickup boolean only                           | Cannot match a pickup place    |
| Delivery coverage | Partial        | free-text `serviceArea` plus delivery boolean | Advisory overlap only          |
| Buyer location    | Yes, free text | `UserIntent.location` / `deliveryArea`        | Advisory overlap only          |
| Service area      | Partial        | same free-text supplier declaration           | Not a normalized set of places |

These must not be collapsed. “Based in Ikeja”, “pickup in Ikeja”, and
“delivers to Ikeja” are distinct statements.

## 3. MATCH / NO_MATCH / UNKNOWN

Current evaluator rules are defensible:

| Evidence                                            | Location result     | Why                                                                      |
| --------------------------------------------------- | ------------------- | ------------------------------------------------------------------------ |
| Buyer text overlaps a declared comma-separated area | MATCH               | Explicit supplier declaration covers the stated text                     |
| Buyer area absent                                   | Not evaluated       | No buyer criterion exists                                                |
| Supplier area absent                                | UNKNOWN             | Missing data is not no coverage                                          |
| Declared `Ikeja`, buyer `Yaba`                      | UNKNOWN             | Free-text names do not establish exclusive boundaries or routing ability |
| `deliveryAvailable=false`, buyer requests delivery  | Fulfilment NO_MATCH | Boolean fulfilment fact, not location inference                          |

Future authoritative **location** NO_MATCH requires all of: buyer and supplier
areas are canonical IDs in the same city vocabulary; supplier coverage is an
explicit complete declared set (not legacy free text); the delivery method is
declared available; and the buyer area is absent from that set. Otherwise it
remains UNKNOWN/advisory.

## 4. Lagos pilot examples

| Case                                                   | Fulfilment    | Location      | Outcome                                              |
| ------------------------------------------------------ | ------------- | ------------- | ---------------------------------------------------- |
| A: delivery Yaba; supplier `Yaba, Akoka`, delivery yes | MATCH         | MATCH         | Retain, high-quality advisory evidence               |
| B: delivery Yaba; supplier `Ikeja`, delivery yes       | MATCH         | UNKNOWN       | Retain; no free-text NO_MATCH                        |
| C: delivery Yaba; area unknown, delivery yes           | MATCH         | UNKNOWN       | Retain and seek confirmation in quote                |
| D: pickup Yaba; pickup yes; pickup point Yaba          | MATCH         | UNKNOWN today | Pickup point is not stored; future model could MATCH |
| E: delivery UNILAG; `Yaba, Akoka`, delivery yes        | MATCH         | UNKNOWN       | UNILAG/landmark aliases are not canonicalized today  |
| F: no buyer location; supplier delivery yes            | Not evaluated | Not evaluated | Retain; no location claim                            |

Current text can include districts (Yaba, Surulere, Ikeja, Lekki), local areas
(Akoka, Maryland, Ojuelegba), landmarks/institutions (UNILAG, UNILAG main
gate, CMS), and vague qualifiers (“around”). They are not interchangeable
administrative units and must not be treated as such.

## 5. Model options and recommendation

| Model                               | Precision / risk                                    | Friction     | Decision                                         |
| ----------------------------------- | --------------------------------------------------- | ------------ | ------------------------------------------------ |
| Free text                           | Explainable but no safe NO_MATCH                    | Lowest       | Keep as legacy/advisory input                    |
| Normalized list of names            | Better, but aliases drift                           | Low          | Insufficient alone without vocabulary governance |
| Controlled `city + area` vocabulary | Explainable, bounded false exclusions               | Low/moderate | **Recommended next step**                        |
| Lat/lng, radius, polygons, maps     | More precise but requires external geographic truth | High         | Not justified for pilot                          |

Proposed canonical representation: `{ country, cityId, areaIds[] }` for
delivery coverage, and an optional distinct `{ cityId, areaId }` pickup point.
The buyer holds `{ cityId, areaId }` only after deterministic selection or a
careful clarification. Raw wording remains available for display/audit, but is
not the matching key. The initial hierarchy is `country → city → area`; do not
add landmarks to the canonical hierarchy. A controlled alias map may map a
small, reviewed set of explicit buyer phrases (for example a campus name) to
an area ID; unrecognized wording stays UNKNOWN.

## 6. Explicit audit evidence required before any authoritative location gate

Do not promote location based on a design review alone. The next implementation
must collect and report, per city and per area vocabulary version:

1. Every supplier coverage declaration with raw value, canonical IDs, method
   (delivery/pickup), operator-review state, and source/version.
2. Every buyer location with raw text, normalization result, alias used (if
   any), confidence/clarification outcome, and whether it remained unknown.
3. Candidate evaluation counts by area/method: MATCH, NO_MATCH, UNKNOWN;
   UNKNOWN rate must be reported separately for legacy and canonical suppliers.
4. A sampled operator audit of canonicalization accuracy, including false
   MATCH and false NO_MATCH findings and ambiguous-expression examples.
5. Trace disagreements and post-quote evidence: supplier confirmations,
   declines caused by coverage, and buyer-reported delivery failures. A quote
   response is evidence, not automatic canonical truth.
6. Coverage completeness: percent of active suppliers with reviewed canonical
   delivery coverage, pickup point where pickup is offered, and explicit
   no-delivery/no-pickup declarations.

Promotion criteria: low and stable UNKNOWN rate among canonical suppliers,
zero unresolved false-exclusion findings in the audit sample, explicit supplier
coverage completeness, reviewed vocabulary/alias changes, and operator approval
of a city-specific calibration report. Until then, NO_MATCH is prohibited for
location and only explicit fulfilment booleans may gate.

## 7. Interaction and representation

Evaluate fulfilment first, then location, then turnaround; never merge them into
one “fit” score. Delivery=yes plus unknown area is `fulfilment=MATCH,
location=UNKNOWN`; pickup=yes does not establish pickup location. Turnaround is
a separate advisory constraint, with quote-level turnaround final after quote.

The same canonical route data should eventually drive a public supplier profile,
agent capability document, and trace. The trace may show buyer-readable area
names and evidence status, never internal IDs. Existing MATCH/NO_MATCH/UNKNOWN
plus candidate confidence is sufficient; do not add a second location confidence
system.

## 8. Phased next milestone

1. Define a versioned, city-scoped vocabulary and reviewed aliases for one Lagos
   pilot area set; no maps or geocoding.
2. Add separate supplier delivery-coverage and pickup-point declarations, while
   preserving legacy `serviceArea` as raw historical evidence.
3. Normalize buyer location only on exact reviewed matches; clarify otherwise.
4. Instrument the evidence set above and run an operator calibration period.
5. Consider an authoritative location NO_MATCH only after the promotion criteria
   are satisfied. This must remain a later explicit decision.

The recommended next milestone is therefore **M10.14: Lagos controlled-area
vocabulary and evidence instrumentation**, not a location gate.
