# M10.1 — Tally → Intra remote business onboarding

**Goal, in one sentence**: a business owner gets a WhatsApp link, fills in a
Tally form on their phone, and a real, correctly-populated Intra business
(and one `DRAFT` route) exists — with no website visit, no account, no
Web3 concept, and no operator re-typing anything.

**Status**: live-verified. The pipeline is deployed to production
(`https://intra-relay.vercel.app/api/onboarding/tally`) and has processed two
real, browser-submitted Tally deliveries end to end — see §16. The Tally
form (`aQR55X`) is `PUBLISHED` with its webhook configured, then manually
**closed** (Tally's "Close form" setting) immediately after those two test
submissions, so it stays reachable only by direct link, not by anyone
stumbling onto it, until a real business is ready to be sent the link. This
document is the implementation record; `docs/M10.1-BUSINESS-ONBOARDING.md` is
the earlier field-audit/contract design that grounded it and is not repeated
here except where it changed.

---

## 1. Existing architecture (what this had to fit into)

Two remote onboarding paths existed before this milestone, audited in
`docs/M10.1-BUSINESS-ONBOARDING.md` §0:

- **Quick-start** (`POST /api/businesses/quick-start`) — the only path with
  real persistence, but it never collects a payout address at all: it always
  writes the zero-address sentinel (`OFF_CHAIN_ASSET`,
  `src/features/commitments/status.ts`).
- **Full onboarding** (`/supplier/onboard/full`) — a richer field set, but
  `buildOnboardingDraft` is client-only (`persistence: "none"`); nothing is
  ever submitted anywhere.

Neither path is a webhook target, and neither was replaced. This milestone
adds a **third** creation path — `processTallySubmission` — that reuses the
same primitives quick-start already established rather than inventing new
ones:

| Primitive needed                         | Reused from                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| Insert a business without a real address | `insertBusiness` (`src/features/businesses/repository.ts`), same as quick-start             |
| "No wallet yet" sentinel                 | `OFF_CHAIN_ASSET` (`src/features/commitments/status.ts`)                                    |
| Create the one live route for a category | `createRoute(db, slug, {})` → `getTemplateForCategory` (`src/features/routes/templates.ts`) |
| Format-validate a payout address         | `EVM_ADDRESS_REGEX` / `normalizeEvmAddress` (`src/lib/address.ts`)                          |
| Duplicate-business detection             | `findBusinessBySlug` (existing) + a new `findBusinessByContactChannelValue`                 |
| Append-only audit trail                  | `appendAuditEvent` (`src/features/audit/repository.ts`)                                     |
| Server-side product analytics            | `forwardServerAnalyticsEvent` (`src/features/analytics/server.ts`, M9.5)                    |
| Operator authentication                  | `requireOperator` (`src/lib/http/operator.ts`)                                              |

`createBusiness` (the public, fully-validated business-creation service) was
**not** reused directly — its own schema hard-requires a regex-valid payout
address (its comment states this explicitly), which is correct for a form
that always has one but wrong for a business that may not have a wallet yet.
Calling `insertBusiness` directly, exactly as `quickStartBusiness` already
does, avoided both duplicating validation logic and loosening
`createBusiness`'s existing contract.

`updatePublishedPricing` (`src/features/routes/pricing.ts`, the existing
`PATCH /api/routes/[id]/pricing` service) is **not** called from this
pipeline. Setting a route's real structured price stays the operator's
existing, already-tested job — see §9 for why.

No new database, automation framework, or CRM was introduced. **No n8n, no
Airtable.** The pipeline is five small modules under `src/features/onboarding/`
plus one webhook route, one operator-read route, one table, and one enum —
directly integrated into the application it already had.

**Resolved by a real live test** (a genuine browser-filled submission on the
published form, through the actual deployed webhook, verified against the

question is the option's own **text**, not an id — confirmed both from the
live webhook delivery and independently from `fetch_submissions`.
`normalize.ts` (§3) already handled this shape defensively (it also handles

That same live test caught a real bug, since fixed: three question labels in
`tally-schema.ts` — `alt_contact`, `business_evidence_link`, and every

because a missing optional field looks identical to a wrong label match.

label-producing function can never catch (the automated test suite's 52
onboarding tests all still passed throughout, before and after the fix,
because the fixture and the code shared the same wrong assumption) — only a
submission against the real, live form could. Fixed by matching the labels
verbatim; re-verified with a second live submission (§16).

## 3. The remote onboarding contract (field mapping)

`src/features/onboarding/tally-schema.ts` maps each question by its exact
label text (not Tally's opaque `key`, which is unconfirmed — see §2) to a
named field. `normalize.ts` reads those labels into a plain
`NormalizedOnboarding` shape, using the **existing** Intra field names as the
target vocabulary (never inventing new field names):

| Tally question (label)                                                              | Normalized field                                                           | Intra target                                                                                                          |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| What is your business name?                                                         | `businessName`                                                             | `businesses.name` (+ derived `slug`)                                                                                  |
| What's your name?                                                                   | `ownerContactName`                                                         | `businesses.contactName`                                                                                              |
| What's your WhatsApp number?                                                        | `whatsappNumber`                                                           | `businesses.contactChannelValue` (`contactChannelType: "whatsapp"`)                                                   |
| Any other way to reach you?                                                         | `altContact`                                                               | not persisted — informational only for the operator's review, not a schema column                                     |
| Which city/area are you based in?                                                   | `city`                                                                     | `businesses.city` (`country` fixed `"Nigeria"`)                                                                       |
| Which areas can you deliver to or accept pick-up from?                              | `serviceArea`                                                              | required for validation (§7); not a dedicated `businesses` column today                                               |
| Can customers pick up / Do you deliver                                              | `pickupAvailable` / `deliveryAvailable`                                    | carried in `normalizedData` for operator review; no existing route/business column for it yet                         |
| Which printing services do you offer?                                               | `services[]` (label per entry)                                             | one route is created per business today (§9) — every selected service is preserved in `normalizedData`, never dropped |
| How do you price `<service>`? / Fixed / Starting from / I need to see the job first | `services[].pricingModel` → `FIXED` \| `STARTING_FROM` \| `QUOTE_REQUIRED` | `quoteRoutes.pricingModel` (`src/features/pricing/model.ts`'s existing enum)                                          |
| What's the price for `<service>`?                                                   | `services[].priceText` (free text, never parsed)                           | operator input to `PATCH /api/routes/[id]/pricing` — never auto-populated (§9)                                        |
| Minimum order, what changes the price?                                              | `services[].notes`                                                         | operator review only                                                                                                  |
| Usual turnaround / reply speed / operating hours                                    | `turnaround` / `responseTime` / `operatingHours`                           | operator review only (no existing SLA-text column; `responseSlaMinutes` stays the template default)                   |
| Do you have a Celo wallet address?                                                  | `hasWallet`                                                                | drives §8's payout logic                                                                                              |
| What's the wallet address?                                                          | `payoutAddress`                                                            | `businesses.payoutAddress` (format-validated, §8)                                                                     |
| How can we see your business is real? / link                                        | `evidenceType` / `evidenceLink`                                            | operator review only                                                                                                  |
| Consent checkbox                                                                    | `consentGiven`                                                             | `businesses.consentAt` (blocking if false, §7)                                                                        |

Fields with no existing Intra column (`serviceArea`, `pickupAvailable`,
`deliveryAvailable`, `turnaround`, `responseTime`, `operatingHours`,
`evidenceType`, `evidenceLink`, every service beyond the one live route) are
**not discarded** — the full normalized object is stored verbatim in
`onboarding_submissions.normalized_data` (jsonb), so an operator sees
everything the business actually said. Extending the schema to give any of
these a first-class column is a future change, not something this milestone
invents a workaround for.

## 4. Webhook contract

`POST /api/onboarding/tally` (`src/app/api/onboarding/tally/route.ts`) is
**the only inbound webhook this application accepts**. Request handling
order, deliberately in this sequence:

1. Read the body as raw text (`request.text()`) — never parsed first.
2. Verify `Tally-Signature` against the raw bytes (§5). Fail closed with
   `503 ONBOARDING_WEBHOOK_UNCONFIGURED` if `TALLY_SIGNING_SECRET` or
   `TALLY_FORM_ID` is unset — this endpoint never falls back to accepting an
   unverified payload.
3. `401 INVALID_SIGNATURE` if verification fails.
4. Only now `JSON.parse` the body (`400 INVALID_JSON` on failure), then
   validate against `tallyWebhookPayloadSchema` (Zod; `400
INVALID_WEBHOOK_PAYLOAD` on shape mismatch).
5. Call `processTallySubmission(db, payload, expectedFormId)` (§8), which
   itself throws `400 UNKNOWN_FORM_ID` if the delivery is for a different
   Tally form.
6. Respond `200 { status, submissionId, businessId, routeId }` — internal
   status codes only ever reach the operator API (§11), never the business
   (§2's Thank You page is the only thing they see).

---

## 5. Signature verification

`src/features/onboarding/signature.ts` — verified against Tally's own
documentation (`tally.so/help/webhooks`): `Tally-Signature` is a
base64-encoded HMAC-SHA256 of the **raw** request body, using the workspace's
per-form signing secret. `verifyTallySignature` computes the HMAC over the
exact bytes received (never a re-serialized parsed object, which can differ
in key order/whitespace and silently break a legitimate signature) and
compares with `crypto.timingSafeEqual` to avoid a timing side-channel. A
missing header, a wrong secret, a tampered body, or a malformed
base64 header are all rejected — tested in `signature.test.ts` and, at the
HTTP boundary, in `route.integration.test.ts`.

---

## 6. Idempotency strategy

The identifier is Tally's own `submissionId` (from `data.submissionId`),
which is `UNIQUE` on `onboarding_submissions.tally_submission_id`.
`insertOrGetOnboardingSubmission` (`src/features/onboarding/repository.ts`)
does one `INSERT ... ON CONFLICT (tally_submission_id) DO NOTHING RETURNING
*`, then re-reads the existing row if the insert did nothing — the same
pattern the codebase already uses for `insertOrGetCommitment`. A redelivered
webhook (Tally retries on non-2xx, and can otherwise redeliver) converges on
the row created the first time and returns `{ status: "REPLAYED", ... }`
with the **same** `businessId`/`routeId` — never a second business, and never
a second `business.created` audit event. No separate idempotency-key
subsystem was built; the existing HTTP-header-keyed `runIdempotent`
(`src/lib/http/idempotency.ts`) was evaluated and correctly not reused — that
helper is for a client-supplied `Idempotency-Key` with request-body hashing,
a different shape of problem than an externally-issued webhook event id.

## 7. Validation rules

`src/features/onboarding/validate.ts`. Two severities, both surfaced to the
operator (§11), only one of them blocking:

- **Blocking** (→ `NEEDS_REVIEW`, no business created at all): missing
  business name / contact name / WhatsApp number / city / service area; no
  consent; zero services selected; an unrecognized pricing-model answer; a
  malformed or zero payout address when a wallet was offered; a likely
  duplicate business (same resulting slug, or the same WhatsApp number under
  a different name).
- **Warning** (business + `DRAFT` route are still created): a service is
  priced `FIXED`/`STARTING_FROM` but the free-text price was left blank. A
  `DRAFT` route can never be quoted to a buyer until an operator activates it
  (`FR-ROUTE-004`), and setting the real, structured price is already the
  operator's existing job (§9) — so this never blocks onboarding, it only
  flags what still needs a price.

Nothing here repairs an ambiguous answer. An unrecognized pricing model or
reply-speed answer is flagged (`normalize.ts`) rather than guessed at, and a
missing structured price is never parsed out of free text (§9) — there is no
established safe parser for Nigerian free-text pricing in this codebase, and
the brief explicitly forbids inventing one for this milestone.

## 8. Business creation flow

`processTallySubmission` (`src/features/onboarding/service.ts`) is the single
entry point:

```
verified webhook → insertOrGetOnboardingSubmission (idempotency, §6)
  → REPLAYED? return the first result
  → normalizeTallySubmission (§3)
  → validateNormalizedOnboarding (§7)
  → blocking issues?  → NEEDS_REVIEW, no business, no route
  → otherwise         → createBusinessFromOnboarding + createRoute → PROCESSED
```

`createBusinessFromOnboarding` calls `insertBusiness` directly (§1) with
`status: "PENDING_VERIFICATION"` (never `ACTIVE` — only an operator
activating a route makes anything buyer-facing) and
`consentAt: new Date()` (consent was just given, in the webhook payload
itself). It appends the same `business.created` audit event
`createBusiness` would have, since that side effect is skipped by calling
the repository function directly.

## 9. Service / route creation flow

One `DRAFT` route is created via the **existing**
`createRoute(db, business.slug, {})` (`src/features/routes/service.ts`),
which resolves its template from the business's own `category` via
`getTemplateForCategory` — never a hardcoded `templateId` string that could
drift from the templates module. Per the existing audit
(`docs/M10.1-BUSINESS-ONBOARDING.md` §0), `printing` has exactly one live
template (`flyer-printing-quote`) today, so a business offering several
printing services still gets one route; every service the business actually
selected is preserved in `normalizedData` (§3) for when the route model
supports independent per-service pricing.

**The free-text price is never parsed into `priceAmount`.** This was a
deliberate mid-implementation correction: the brief explicitly forbids
parsing arbitrary natural-language pricing without an established safe
parser, and Intra has none. The route is created with only the template's
safe defaults; the business's own pricing intent (model + free text + notes)
is preserved verbatim in `normalizedData` for an operator to read and enter
through the pre-existing, already-tested
`PATCH /api/routes/[id]/pricing` / `EditPublishedPriceForm` flow before ever
activating the route.

## 10. Payout handling

`hasWallet` drives the outcome, never a guess:

- **No wallet offered** (`hasWallet: false`/unanswered) → the business is
  onboarded with `payoutAddress: OFF_CHAIN_ASSET` (the same zero-address
  sentinel `quickStartBusiness` already uses) — never a fabricated non-zero
  placeholder. `payment_ready` stays false by construction (routes can only
  be quoted once `ACTIVE`, and activation's own checklist is unaffected by
  this milestone).
- **Wallet offered with an address** → format-validated with the existing
  `EVM_ADDRESS_REGEX`/`normalizeEvmAddress` (`src/lib/address.ts`). A
  malformed address, or the literal zero address offered _as_ a real
  address, is a **blocking** validation issue (§7) — treated as a data
  problem to review, never silently downgraded to "no wallet" (this mirrors
  M10.5's own fund-loss-prevention fix for the same sentinel).
- **Wallet offered with a valid address** → stored directly on
  `businesses.payoutAddress`.

No private key, seed phrase, password, or API secret is ever asked for or
accepted — the form has no such question, and nothing in this pipeline reads
one.

## 11. Onboarding states

A deliberately small, new enum — `onboarding_submissions.status`
(`RECEIVED | NEEDS_REVIEW | PROCESSED | REJECTED`,
`src/features/onboarding/status.ts`) — tracking **only** whether a webhook
delivery was successfully turned into a real business. It does not duplicate
or compete with the business's own commercial lifecycle, which stays exactly
where it already lived:

| Brief's concept    | Where it actually lives                                                                                                                                                                                                                                                                                                                              |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Submitted          | `onboarding_submissions.status = RECEIVED` (signature+shape verified, not yet processed)                                                                                                                                                                                                                                                             |
| Needs review       | `onboarding_submissions.status = NEEDS_REVIEW` — no business exists yet                                                                                                                                                                                                                                                                              |
| Approved / created | `onboarding_submissions.status = PROCESSED` + a real `businesses` row (`PENDING_VERIFICATION`) + one `DRAFT` route                                                                                                                                                                                                                                   |
| Pilot ready        | the **existing** `quoteRoutes.status = ACTIVE` (an operator activates it exactly as they would any other route) — reused, not a new state                                                                                                                                                                                                            |
| Rejected           | `onboarding_submissions.status = REJECTED` — reserved for a delivery that never reached normalization (bad signature, unknown form, malformed payload); today those fail as HTTP errors before a row would need this status, so it exists for forward-compatibility with a future async/queued delivery path, not currently written by any code path |

## 12. Operator workflow

No new dashboard was built. `GET /api/operator/onboarding`
(`src/app/api/operator/onboarding/route.ts`, `requireOperator`-gated) lists
every submission — `status`, the full `normalizedData`, `issues`
(blocking + warnings), and the linked `businessId`/`routeId` once one exists.
This exists specifically for `NEEDS_REVIEW` rows, which create no business
and so would otherwise be invisible to the operator (a `PROCESSED` row's
business/route is already visible through the existing operator review
surfaces). An operator never re-types anything the business already
answered — everything is already structured JSON on the submission row.

## 13. Error handling

- **Webhook boundary** (§4): every failure is a typed `HttpError` with a
  stable `code` (`INVALID_SIGNATURE`, `INVALID_JSON`,
  `INVALID_WEBHOOK_PAYLOAD`, `UNKNOWN_FORM_ID`,
  `ONBOARDING_WEBHOOK_UNCONFIGURED`) — never a raw stack trace or a silent
  200 on a bad request.
- **Data problems** (missing fields, bad payout address, likely duplicate):
  never an error response. `processTallySubmission` never throws for a data
  problem — it returns `NEEDS_REVIEW` with a `200`, so Tally does not
  retry-storm a submission that will never validate no matter how many times
  it's redelivered.
- **A genuinely unexpected failure** (e.g. a database error mid-pipeline)
  propagates as a `500` through the same `route()`/`HttpError` wrapper every
  other endpoint uses — nothing onboarding-specific was added here.

---

## 14. Security & privacy

- The webhook is signature-gated and fails closed when unconfigured (§4–5).
- No prohibited data is ever asked for, accepted, or stored: no seed phrase,
  private key, password, BVN/NIN, or bank/card credential — the form has no
  such question.
- The only wallet-related value handled is a **public** address, and only
  after format validation (§10).
- Analytics (`src/features/analytics/events.ts`, six new events —
  `onboarding_received`, `onboarding_validated`, `onboarding_needs_review`,
  `onboarding_created`, `onboarding_pilot_ready`, `onboarding_failed`) never
  carries raw form content — only counts (`service_count`, `issue_count`,
  `warning_count`) and a `reason_code`, run through the same `sanitizeProps`
  every other event goes through. All six are server-forwarded
  (`SERVER_FORWARDED_EVENTS`) since a Tally webhook has no browser actor.
- The operator listing (§12) is `requireOperator`-gated like every other
  operator surface; nothing about it is publicly reachable.

## 16. Live verification (real Tally → Intra test, 2026-09-11)

Everything above is deterministic and automated. This section is the one
thing automation cannot substitute for: a genuine submission through the
real, published Tally form, over the real webhook, into the real production
database — done twice, from this session, with the user's explicit
authorization at each state-changing step (deploying to production,
publishing the form, applying the migration).

**Environment**: the `feat/m10.1-tally-onboarding` working tree (uncommitted
at the time) was deployed straight to production —
`https://intra-relay.vercel.app` — via `vercel --prod`, since Tally only
exposes webhook configuration on a _published_ form with no MCP/API path
for it (confirmed: no webhook-related tool exists in the Tally MCP toolset;
Tally's own docs anchor it to "Publish your form and go to the Integrations
tab"). `TALLY_FORM_ID` and `TALLY_SIGNING_SECRET` were set as Vercel
production env vars (the latter entered directly via `vercel env add` by the
user — it never passed through this session). Migration `0012` was applied
to the real database by the user, using the project's own manual-migration
convention (§6.2 of `CLAUDE.md`) — not by this session directly, since
bulk-pulling all production secrets to apply it was correctly blocked by the
permission classifier.

**Test 1** — a real browser session filled and submitted the live form
(`M10.1 Test Printer`, 3 services across all 3 pricing models, no wallet).
Result: `PROCESSED`, `200` response (confirmed via `vercel logs
--status-code 200`, not just application logs), a real `businesses` row
(`PENDING_VERIFICATION`, `OFF_CHAIN_ASSET` payout) and one `DRAFT`
`quote_routes` row, verified by direct read-only SQL against the production
database (`scripts/verify-m10-1-test-submission.mjs`, run by the user with a
`DATABASE_URL` they pulled themselves — never exposed to this session).

This test caught a real bug: `alt_contact`, `business_evidence_link`, and
every service's pricing `notes` label in `tally-schema.ts` carried a
parenthetical suffix (e.g. "... (optional)") that this session had _typed_
when building the form's _intent_, but the live form's actual question text
never got that exact suffix. `normalize.ts`'s `byLabel` matches labels
exactly, so all three fields silently normalized to `null` — every business
that filled them in would have had that input discarded, with no error, no
issue recorded, nothing to indicate anything was wrong (a filled-in optional
field and a skipped one look identical downstream). The automated test
suite could not have caught this: its fixtures are generated from the exact
same `servicePricingLabels`/`NON_SERVICE_FIELD_LABELS` functions the
production code uses, so a wrong label and a fixture built from that same
wrong label always agree with each other. Only a submission against the
real, independently-built form could expose the mismatch.

Fixed by matching the three labels verbatim to the live form (`tally-schema.ts`).
Confirmed by rerunning `tsc`/`lint`/the full test suite (unaffected — the
fixtures regenerate from the corrected function automatically) and
redeploying to production.

**Test 2** — a second real submission (`M10.1 Test Printer 2`), values
